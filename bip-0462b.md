# Abstract

This BIP, working name **BIP 462b**, is a soft-fork alternative to BIP 462. It takes BIP 462's security budget, 0.30% of supply per year, as a **target**, and charges a **demurrage** for the part that the block subsidy does not cover. Following a design sketched by Peter Todd, the demurrage is not levied continuously on every unspent output. It is **charged when an output is spent**, and paid into a **pool of future mining revenue**. The target is therefore an upper bound, not a floor: miners receive the demurrage only as outputs are spent, and never from outputs that are not.

When a block spends an output, it owes a charge equal to the fall in a demurrage index since the block that created the output. The coinbase must pay the block's total charges into a pool output. Every block then draws a fixed fraction of the pool through a deterministic claim transaction, whose fee the coinbase collects. Transactions are unchanged: the charge comes out of the fees they pay. The rate depends only on the subsidy schedule, so it is known decades in advance. It is zero until the 2032 halving.

Every rule restricts what nodes already accept, so nodes that do not upgrade keep following the chain, provided that effectively all hashrate enforces the rules once charges begin. The BIP is deployed in two stages, so that charges begin only after miners have signalled that they can build the blocks the rules require. There is no change to the transaction format, signature hashes or the UTXO set's format. No transaction that can be signed today becomes invalid, except one that creates or spends an output with the script this BIP reserves. A transaction whose fee cannot be raised to cover its charge stays valid, but may be unable to confirm. Supply is unchanged: output values keep their meaning, and the issuance schedule and the 21,000,000 BTC limit apply to them as they do today.

# Motivation

BIP 462 sets out the case for a security budget floor: the subsidy halves towards zero, fees have not replaced it, and the recurring payments to miners must stay large relative to the value that an attack could capture or destroy (Budish, 2018). This BIP shares that motivation and the 0.30% target. It changes how the budget is funded and deployed. In exchange it gives up BIP 462's guarantee that the target is met (see Realised budget).

BIP 462 is a hard fork. It mints a dividend in the coinbase and revalues every unspent output each block, so every node must upgrade. Output values stop meaning what they say: wallets must convert them to effective values, and denominate each transaction's outputs at a reference height that it inherits from its inputs. Nodes must track the value of the whole UTXO set, which takes one scan of it, and a reference height for every output.

A soft fork can only add restrictions. It cannot create value, change the value of an unspent output, or spend an output without its owner's signature. It can, however, require each block to pay something out of value the block already controls. Peter Todd observed that demurrage "could in theory be implemented in a soft-fork" (bitcoin-dev, 23 June 2022): transactions would be required to include an output paying the demurrage into a pool of future mining fees. He doubted then that this was practical. His talk *Tail Emissions and Demurrage* (Bitcoin++ Toronto, July 2026) returned to the idea, as reported: a charge applied when coins are finally spent, with the proceeds going to a fund that miners draw from.

This BIP specifies that mechanism, with three refinements:

- The charge is owed by the **block**, and the coinbase pays it, rather than by each transaction through an output of its own. As a result no transaction's validity depends on the charge, and pre-signed transactions stay valid.
- The pool is held in ordinary outputs, which nodes that do not upgrade already accept. It is drawn down by a deterministic transaction that nothing can malleate.
- Fees are paid to the block producer as today and do not affect the rate, as in BIP 462.

| | BIP 462 | This BIP |
|---|---|---|
| Deployment | hard fork | soft fork |
| What decays | every unspent output, every block | an output, when it is spent, by the decay since its creation |
| Paid to miners | dividend minted in the coinbase | charges pooled, then claimed as a fee |
| The 0.30% target | a floor: the dividend is claimed every block, as decay accrues | an upper bound: demurrage arrives when outputs are spent |
| Transaction fees | to the block producer, not counted towards the target | the same |
| Rate | set each period from the subsidy schedule and the value of the UTXO set | fixed by the subsidy schedule |
| Lost coins | recycled to miners | never pay |
| Supply | effective supply follows the schedule; nominal values can exceed it | unchanged |
| Output values | nominal; worth their effective value at a reference height | keep their meaning; an output owes a public charge when spent |
| Transaction format, signature hashes, TRUC (BIP 431) | unchanged | unchanged |
| Pre-signed transactions | stay valid, and their validity does not depend on when they are mined | stay valid; confirming them needs a fee that covers the charge |
| New consensus state | index, rate, UTXO set value, a reference height per output; one UTXO set scan | index schedule; the pool is in the UTXO set |

# Specification

## Overview

1. A **demurrage index** `I(h)` falls each block by a rate fixed for each **rate period** (2,016 blocks on mainnet). The rate makes up the shortfall of the block subsidy against 0.30% of the scheduled supply per year. It depends only on height.
2. When a block spends an output, it owes a **charge** equal to the output's value times the fall in the index since the block that created it.
3. The coinbase must pay the block's total charges into a **pool output**.
4. The second transaction of every block, the **claim transaction**, spends the pool outputs that have become spendable and returns all but a fixed fraction of their value to the pool. That fraction is the claim transaction's fee, which the coinbase collects like any other fee.
5. Transaction fees are paid to the block producer, as today, and do not affect the rate.
6. The rules take effect in two stages. The restrictions on the pool script apply from `ACTIVATION_HEIGHT`. The index starts to fall at `CHARGE_HEIGHT`, once miners have signalled that their block-building software is ready.

## Parameters

```
TARGET_RATE_ANNUAL      = 0.0030             (0.30% of scheduled supply per year)
BLOCKS_PER_YEAR         = 52,560             (≈ 144 blocks/day)
TARGET_RATE_PER_BLOCK   = TARGET_RATE_ANNUAL / BLOCKS_PER_YEAR
                        = TARGET_NUM / TARGET_DEN
                        = 3 / 52,560,000     (≈ 5.708e-8)
RATE_PERIOD             = the deployments' signalling period (2,016 blocks on mainnet)
POOL_DIVISOR            = 10,000             (pool half-life ≈ 6,931 blocks, about 48 days)
INDEX_ONE               = 10^18              (fixed-point scale of the index and the rate)
POOL_SCRIPT             = 0x04706f6f6c7551   (PUSH4 "pool" OP_DROP OP_1)
COINBASE_MATURITY       = 100                (existing consensus rule)
ACTIVATION_HEIGHT       = the first height at which the demurrage deployment is active (see Deployment)
CHARGE_HEIGHT           = the first height at which the demurrage and demurrage_charges
                          deployments are both active (see Deployment)
CHARGE_MARGIN           = 144                (policy only; see Relay and mining policy)
CHARGE_TOLERANCE        = 1,000 satoshis     (policy only; see Relay and mining policy)
```

This BIP has two version bits deployments with the same signalling period. `ACTIVATION_HEIGHT` is when nodes begin to enforce its rules. `CHARGE_HEIGHT` is when the index starts to fall, so no block owes a charge before it. By definition `CHARGE_HEIGHT ≥ ACTIVATION_HEIGHT`.

Version bits deployments activate at the start of a signalling period, so both heights are multiples of `RATE_PERIOD`. A deployment that fixes either height instead, for example once it is buried, must keep it a multiple of `RATE_PERIOD`. On mainnet the signalling period is the 2,016-block difficulty adjustment period, so rate periods coincide with difficulty adjustment periods.

`POOL_SCRIPT` is a bare script that anyone can satisfy with an empty scriptSig under the current rules. It matches no standard output type, so current policy refuses to relay transactions that create an output with it or spend one. Every restriction this BIP places on it therefore applies only to transactions that nodes already refuse to relay.

`block_subsidy(i)` is the existing subsidy schedule: `floor(50 × 10^8 / 2^floor(i / SUBSIDY_HALVING_INTERVAL))` satoshis, or zero once `floor(i / SUBSIDY_HALVING_INTERVAL)` reaches 64. `SUBSIDY_HALVING_INTERVAL` is the network's halving interval (210,000 on mainnet).

## Test networks

Testnet3, testnet4 and signet use the mainnet values. On regtest, the signalling period is 144 blocks and the subsidy halves every 150 blocks. With the mainnet target, the subsidy would cover the target, and every charge would be zero, for the first 2,400 blocks or so. Regtest therefore uses:

```
RATE_PERIOD             = 144
TARGET_NUM / TARGET_DEN = 1 / 2,000
```

With `CHARGE_HEIGHT` at 432, the first rate period then has a zero rate, as on mainnet before 2032, and charges begin at height 576. Other test networks may choose their own target.

## Fixed-point arithmetic

All arithmetic is performed on integers. Floating-point arithmetic must not be used.

- Amounts are integers in satoshis.
- The index `I(h)` and the per-block rate `r_k` are integers scaled by `INDEX_ONE`: an index of `INDEX_ONE` means 1.0, and a rate of 57,077,625,570 means about 5.708e-8 per block.
- Every division rounds down (`floor`). Intermediate products fit in 128 bits, but not in 64: on mainnet, `S_k × RATE_PERIOD × TARGET_NUM` already exceeds 2^63.

## Demurrage rate

Rate period `k` (for `k = 0, 1, 2, …`) begins at height `H_k = CHARGE_HEIGHT + k × RATE_PERIOD` and covers `RATE_PERIOD` blocks. Its rate is:

```
S_k          = sum of block_subsidy(i) for 0 ≤ i < H_k               (scheduled supply)
subsidy_k    = sum of block_subsidy(i) for H_k ≤ i < H_k + RATE_PERIOD
target_k     = floor(S_k × RATE_PERIOD × TARGET_NUM / TARGET_DEN)
shortfall_k  = max(0, target_k − subsidy_k)
r_k          = floor(shortfall_k × INDEX_ONE / (RATE_PERIOD × S_k))     (r_k = 0 if S_k = 0)
```

`block_subsidy(i)` is the schedule amount (see Parameters), whatever any coinbase actually claimed. `S_k` includes the genesis block's subsidy. `S_k` is zero only when `CHARGE_HEIGHT` is zero, as on test networks where both deployments are always active.

By construction `0 ≤ r_k ≤ floor(INDEX_ONE × TARGET_NUM / TARGET_DEN)`, which is 57,077,625,570 on mainnet. The rate of a period depends only on its first height `H_k`. Because `CHARGE_HEIGHT` is a multiple of `RATE_PERIOD`, the rate periods, and so the rate at each height from `CHARGE_HEIGHT` on, are the same whatever its value. The rate of every future period is therefore known today. On mainnet, for the first rate period wholly within each halving era:

| Period | Scheduled supply | Target | Subsidy | Shortfall | Annual rate |
|---|---|---|---|---|---|
| until 2032 (height < 1,260,000) | ≤ 20.67M | ≤ 62,016 | ≥ 82,125 | 0 | 0% |
| 2032–2036 | 20.67M | 62,016 | 41,062 | 20,953 | 0.101% |
| 2036–2040 | 20.84M | 62,510 | 20,531 | 41,979 | 0.201% |
| 2040–2044 | 20.92M | 62,755 | 10,266 | 52,489 | 0.251% |
| 2044–2048 | 20.96M | 62,877 | 5,133 | 57,744 | 0.275% |
| after 2140 | 21.00M | 63,000 | 0 | 63,000 | 0.300% |

Amounts in BTC per year. The annual rate is the compounded fall of the index over a year at the period's rate, `1 − (1 − r_k / INDEX_ONE)^52,560`. The simple rate, `r_k × 52,560 / INDEX_ONE`, is less than 0.0005 percentage points higher: 0.2755% rather than 0.2751% in 2044–2048, and 0.3000% rather than 0.2996% after 2140. The first period with a non-zero rate begins at height 1,260,000, which is both the 2032 halving and a multiple of 2,016. Its rate is 19,284,730,634.

## Demurrage index

`I(h) = INDEX_ONE` for every `h < CHARGE_HEIGHT`. For each block `h` in rate period `k`:

```
I(h) = max(1, floor(I(h−1) × (INDEX_ONE − r_k) / INDEX_ONE))
```

The index is non-increasing. It starts falling only at `CHARGE_HEIGHT`, so a later start skips the decay that a non-zero rate would have caused before it. On mainnet, for any `CHARGE_HEIGHT` up to 1,260,000, it depends only on height: it stays at `INDEX_ONE` until height 1,259,999. It then falls by 0.41% by the 2036 halving, 1.21% by the 2040 halving and 2.19% by the 2044 halving.

The lower bound of 1 keeps the index from reaching zero, which at the full target rate would take about 8,600 years. The index falls below 10^9 after about 6,900 years, and charges lose precision long before it bottoms out, so the scale would need revisiting within millennia.

## Demurrage charge

An input spending an output of value `v` created in the block at height `c`, included in the block at height `h`, has the charge:

```
charge(v, c, h) = v − floor(v × I(h) / I(c))
```

- `c` is the height already recorded with every unspent output. An output created before `CHARGE_HEIGHT` has `I(c) = INDEX_ONE`, so it pays only for decay from `CHARGE_HEIGHT` on.
- An output created and spent in the same block has a charge of zero.
- Rounding down the remaining value rounds the charge up, by less than one satoshi. As a result, an input pays at least one satoshi whenever its output has a non-zero value and the index has fallen since the output was created.
- Inputs of the claim transaction have no charge.

The **block charge** `C(h)` is the sum of the charges of every input of every non-coinbase transaction in block `h`, except the claim transaction's inputs. The coinbase input spends no output and has no charge. `C(h)` does not depend on the order of transactions.

The charge is not deducted from any transaction. A transaction's fee is still the sum of its input values less the sum of its output values. What the block's miner keeps from a transaction, its **net fee**, is its fee less its charge.

## Pool outputs

A **pool output** is an output whose scriptPubKey is exactly `POOL_SCRIPT` and that was created in a block at height `ACTIVATION_HEIGHT` or later. From `ACTIVATION_HEIGHT`:

1. Only a coinbase or a claim transaction may create an output with `POOL_SCRIPT`.
2. A pool output may be spent only by a claim transaction.

Outputs with `POOL_SCRIPT` created before `ACTIVATION_HEIGHT`, if any exist, are not pool outputs and are unaffected.

## Coinbase contribution

If `C(h) > 0`, the coinbase must create exactly one pool output, the block's **contribution**, with value exactly `C(h)`. If `C(h) = 0`, the coinbase must not create a pool output.

The contribution is exact so that no miner can start the pool before any charge is owed. A voluntary contribution would make a claim transaction mandatory in every later block, and make the blocks of miners that have not upgraded invalid years early.

The coinbase value limit is unchanged: subsidy plus fees. Fees include the claim transaction's fee. The miner therefore keeps `block_subsidy(h) + fees − contribution`.

## Claim transaction

The **pool inputs** of block `h` are, in this order:

1. the **carry**: output 0 of the claim transaction of block `h − 1`, if that block has one;
2. the **matured contribution**: the contribution of block `h − COINBASE_MATURITY`, if that block has one.

These are the only pool outputs that are spendable at height `h`. Every earlier carry and contribution was spent by an earlier claim transaction, and later contributions are immature coinbase outputs.

In terms of the UTXO set before block `h`, the unspent pool outputs are therefore:

- the carry, which is the only one not created by a coinbase;
- the contributions of blocks `h − COINBASE_MATURITY` to `h − 1`, which are all created by a coinbase. The matured contribution is the one created at height `h − COINBASE_MATURITY`.

The UTXO set records each output's height and whether a coinbase created it. A node can therefore find the pool inputs in two ways. It can read blocks `h − 1` and `h − COINBASE_MATURITY`. Or it can scan the UTXO set once for `POOL_SCRIPT` outputs created at or after `ACTIVATION_HEIGHT` and then track them as blocks connect, for example after loading an assumeutxo snapshot. A node that prunes blocks, or that started from a snapshot, does not hold every block below the ones it may have to connect or verify again. It should therefore keep the carry and the unspent contributions as part of its chain state, and not rely on reading blocks.

If block `h` has any pool input, its second transaction (index 1) must be its claim transaction, which must be exactly:

```
nVersion   = 2
inputs     = the pool inputs, in the order above, each with an empty scriptSig,
             nSequence = 0xFFFFFFFF and an empty witness
outputs    = one output: value = P − floor(P / POOL_DIVISOR), scriptPubKey = POOL_SCRIPT
nLockTime  = 0
```

where `P` is the sum of the values of the pool inputs. Its fee, `payout(h) = floor(P / POOL_DIVISOR)`, is the block's **pool payout**.

A block with no pool input has no claim transaction. A carry is always at least one satoshi, so once a claim transaction has occurred, every later block has one. No two claim transactions spend the same output, so no two have the same txid.

## Summary of new block rules

From `ACTIVATION_HEIGHT`, a block at height `h` is invalid unless, in addition to the existing rules:

1. no transaction other than its coinbase and its claim transaction creates an output with `POOL_SCRIPT`, and no transaction other than its claim transaction spends a pool output;
2. its coinbase creates exactly one pool output, of value `C(h)`, if `C(h) > 0`, and none otherwise;
3. if it has pool inputs, its transaction at index 1 is the claim transaction specified above.

## Supply

This BIP creates no value and destroys none. Charges move value from the spenders of outputs into the pool, and the pool pays it out to miners as fees. The sum of all unspent output values, pool outputs included, follows the existing issuance schedule and never exceeds 21,000,000 BTC. Unlike in BIP 462, nominal values keep their meaning: an output's effective value is its value less a charge that anyone can compute.

## Effective value

Effective value is not a consensus concept. It is what an output is worth to its owner, net of the charge it would owe if spent in the next block `h`:

```
effective_value(v, c, h) = floor(v × I(h) / I(c))
```

An output's charge is public and deterministic. Anyone can compute it from its value and its confirmation height.

## Realised budget

The rate is set so that subsidy plus demurrage would equal the target if every output paid its decay as it accrued. Outputs pay only when they are spent, so miners receive less. This section defines the difference. It is not a consensus rule.

```
paid(h)        = sum of C(i) for every i ≤ h
outstanding(h) = sum of charge(v, c, h) over the outputs, other than pool outputs,
                 that are unspent after block h
accrued(h)     = paid(h) + outstanding(h)
pool(h)        = sum of the values of the pool outputs that are unspent after block h
```

Each block adds to `accrued` the fall in effective value of every output that existed before it, about `r_k` times their total effective value. `r_k` was computed from the shortfall over the whole scheduled supply, so this is the per-block shortfall or slightly less. Every satoshi contributed is either still in a pool output or has been paid out, so the pool payouts up to block `h` total:

```
paid(h) − pool(h) = accrued(h) − outstanding(h) − pool(h)
```

Miners' revenue from demurrage is what has accrued, less what unspent outputs still owe, less what the pool still holds. Counted from the first charge, subsidy plus payouts therefore stays below the target. A single period can exceed it, when outputs that were idle for long are spent. The budget falls short of the target in three ways:

- **While `outstanding` grows.** It grows from the first block with a non-zero rate, for as long as old outputs stay unspent. If half the supply by value is not spent between 2032 and 2036, half or more of the demurrage accrued in those years is still outstanding at the end of them.
- **By the level `outstanding` settles at.** It stops growing only when outputs are spent as fast as charges accrue. It is then about `A` years of accrual, where `A` is the average age of unspent outputs weighted by value. An average age of four years would leave about 250,000 BTC outstanding at the full target rate.
- **For outputs that are never spent.** They never pay. Their outstanding charge grows towards their whole value.

The pool adds a shorter delay. It holds about `POOL_DIVISOR` blocks of contributions.

## Relay and mining policy

These recommendations are not consensus rules.

- **Mining score.** Nodes rank transactions, packages and clusters by **net fee**: the fee less a **policy charge**, which is the transaction's charge at an **evaluation height** `E_tx` of its own. Net fees fall by about `r_k` times the input value for each block a transaction waits. That is in proportion to value rather than size. Re-evaluating every transaction every block would reorder the mempool every block. Evaluating every transaction far ahead would make each one pay for decay it will not owe: 144 blocks of margin on a 1,000 BTC input is about 820,000 satoshis at the full target rate, and it would go to the miner that includes the transaction, not to the pool. Nodes therefore look up to `CHARGE_MARGIN` blocks ahead, but no further than costs the transaction `CHARGE_TOLERANCE`:

  ```
  charge_at(e) = sum of charge(v, c, e) over the transaction's inputs
  E_tx         = the greatest e such that n ≤ e ≤ n + CHARGE_MARGIN
                 and charge_at(e) − charge_at(n) ≤ CHARGE_TOLERANCE
  ```

  where `n` is the next block's height when the node computes `E_tx`. The policy charge is `charge_at(E_tx)`. It is never less than the transaction owes in a block up to `E_tx`, and exceeds that by at most `CHARGE_TOLERANCE`. At the full target rate, a transaction that spends up to about 1.2 BTC is evaluated 144 blocks ahead, one that spends 10 BTC 17 blocks ahead, and one that spends more than about 175 BTC at the next block's height.
- **Re-evaluation.** A node computes `E_tx` when it accepts a transaction, again each time the next block's height exceeds `E_tx`, and for every transaction after a reorganisation. A transaction that spends little is therefore re-evaluated every 145 blocks, at heights that depend on when it was accepted, and one that spends much is re-evaluated more often. Nodes do not evict a transaction because its net fee has fallen. It stays in the mempool, ranked by its new net fee, until it is mined, replaced or expires, or until it is trimmed when the mempool is full. Evicting it would let its sender broadcast a conflicting transaction without paying to replace it, which is free relay. It would also drop a transaction that a child could still bump.
- **Unconfirmed inputs.** An input that spends an output of an unconfirmed transaction is charged as if that output were created in the next block: `c = n` in `charge_at`. The parent cannot confirm earlier, so this is the most the input can owe at `E_tx`. A transaction's net fee therefore does not fall when its parent confirms, only when it is re-evaluated. If parent and child confirm in the same block, the input owes nothing, and the child has overpaid by at most `CHARGE_TOLERANCE`. The margin is the same as any other input's: 144 blocks for a small one, and none for one whose charge grows by more than `CHARGE_TOLERANCE` a block. A child that spends an output that large has a policy charge of zero, and owes a block of decay as soon as its parent confirms without it (see Open Questions).
- **Before charges begin.** `CHARGE_HEIGHT` is known once each deployment is locked in or active, and nodes compute policy charges from it. Before that, they charge nothing. `CHARGE_HEIGHT` is then more than one signalling period away. A signalling period is at least `CHARGE_MARGIN` blocks on every network, so no evaluation height reaches `CHARGE_HEIGHT`, and every policy charge would be zero anyway.
- **Relay.** A transaction is accepted if its net fee meets the minimum relay feerate, or if it belongs to a package whose net fee does. Each transaction therefore pays the minimum relay feerate, net of its charge, if it is mined by its evaluation height. A wallet that wants a transaction to stay above that feerate for longer adds a margin of its own. A transaction's net fee may be negative. Its descendants then pay its charge, as children pay for zero-fee parents today. Package and mempool trimming rules compare net fees. TRUC rules are unchanged.
- **Replacement.** Replacement (RBF) rules compare net fees. For each transaction it would replace, a node uses the greater of that transaction's net fee now and its net fee when it was accepted. Net fees fall as transactions wait. Without this rule, a transaction that spends only one input of an older one could replace it for less than the fee the older one was relayed on.
- **Fee rules.** Rules that require a transaction's fee to have a particular value compare the fee, not the net fee. In particular, a transaction with ephemeral dust must still have a fee of zero. The child that spends the dust pays the parent's charge, as part of the package. Fee estimation should estimate net feerates.
- **Pool outputs.** Nodes do not relay or accept into their mempool any transaction that creates an output with `POOL_SCRIPT` or spends a pool output. Claim transactions exist only in blocks. A claim transaction from a disconnected block is not returned to the mempool.
- **Block assembly.** The miner selects transactions by net feerate. It can use the mempool's net fees, which understate what each transaction is worth in the next block by at most `CHARGE_TOLERANCE`. It computes the block charge exactly, at the block's height. It places the claim transaction at index 1, creates the contribution in the coinbase and claims the rest of the subsidy and fees. The contribution can exceed the block's subsidy and fees only if the miner has prioritised a transaction by hand. The miner then leaves that transaction out, unless it adds a transaction of its own that pays the difference as a fee (see Backward Compatibility).
- **Compact blocks.** The claim transaction is never in a mempool. A node that implements this BIP prefills it in the compact blocks (BIP 152) it sends, as it does the coinbase. When a block it receives lacks the claim transaction, it builds it, since the chain determines it. Between two nodes that do not implement this BIP, neither happens. Once claim transactions begin, every block one of them relays to the other costs a `getblocktxn` round trip.
- **Checking before relay.** A node that relays blocks before validating them in full, as in high-bandwidth compact block relay, should first check that a block whose parent is its tip has the expected claim transaction at index 1. Once claim transactions have begun, this check is cheap and stops the blocks of miners that have not upgraded from reaching other nodes through upgraded ones (see Security Considerations). It does not check the contribution, which needs the block's inputs.

## getblocktemplate

Each deployment has a `getblocktemplate` rule (BIP 9) of the same name. A client that builds coinbases with the contribution, and keeps the claim transaction in place, declares both.

`demurrage` is optional at every height. Nodes signal for it whether or not the client declares it. Its signalling then measures how many nodes have upgraded, which is what enforcement needs: a miner whose node does not enforce this BIP builds invalid blocks once charges begin, whatever its mining software. Tying this signal to the mining software would make miners upgrade both at the same time, and make the node upgrade harder.

`demurrage_charges` measures the other half: whether the software that builds the block is ready. While it is signalling, it is listed in `vbavailable` as `!demurrage_charges`, and a node sets its bit only in templates for clients that declare the rule. Once it is active, it is listed in `rules`. It is optional until the start of the first rate period with a non-zero rate: height 1,260,000 on mainnet, if `CHARGE_HEIGHT` is not later. From that height it is listed as `!demurrage_charges`, as segwit's is listed as `!segwit`, and a client that does not support this BIP refuses the template. Without the required rule, such a client would build coinbases without the contribution, and every block it built would be invalid.

The rule is optional until then because, until then, a client that does not support this BIP can use a template as it is. No block owes a charge, so none needs a contribution or a claim transaction. A refused template stops a miner from building a block. It cannot make the miner build an invalid one. The switch can therefore wait until templates change. From `ACTIVATION_HEIGHT`, when a client that does not declare `demurrage_charges` requests a template, nodes should warn, for example in their logs, that templates will require the rule, and from which height once `CHARGE_HEIGHT` is known.

From `ACTIVATION_HEIGHT`, a template also:

- lists the claim transaction, when the block needs one, as the first entry of `transactions`, with the pool payout as its `fee`;
- gives each transaction's `charge` at the template's height, beside its `fee`. Inputs that spend outputs of earlier transactions in the template have no charge;
- gives `demurrage_contribution`, the block charge `C(h)` in satoshis. If it is not zero, the client must add one output of that value, with scriptPubKey `POOL_SCRIPT`, to the coinbase;
- sets `coinbasevalue` to what the coinbase may pay to the miner's own outputs: `block_subsidy(h) + fees − C(h)`, where `fees` includes the pool payout.

A client that leaves out a transaction must leave out its descendants too, as today. It then lowers `demurrage_contribution` by the transaction's charge and `coinbasevalue` by its net fee. It must not leave out the claim transaction or move it from index 1.

## Fees and interfaces

A transaction's fee is unchanged: its input values less its output values. From the first charge, part of the fee is the charge, which the block passes to the pool, and the rest is the net fee. Software that reads a fee or a feerate as what a miner earns must use the net fee instead. This section is not a consensus rule.

- **Node interfaces.** Wherever a node reports the fee of an unconfirmed transaction, it should also report the policy charge, the height it was evaluated at and the net fee. Wherever it reports an unspent output, it should be able to report the output's charge in the next block and its effective value. Fee estimates are net feerates. The caller adds the charge of the inputs it spends.
- **PSBT.** A per-input field carries the height of the block that confirmed the output the input spends, as a 32-bit little-endian integer. It is absent when that output is unconfirmed. Its type is to be assigned in BIP 174's registry. With it, a signer that knows the height at which the transaction is expected to confirm can show the charge and the net fee separately.
- **Signers that cannot check the height.** The confirmation height in a PSBT is a claim by whoever built it, and an understated height turns part of an excessive fee into an apparent charge. A signer can still bound the charge. At height `h` no input owes more than `v − floor(v × I(h) / INDEX_ONE)`, and `I(h)` depends only on `h` and `CHARGE_HEIGHT`. A signer should treat any part of the fee above that bound as net fee, and apply its usual fee checks to it.
- **Transactions with inputs from several parties**, such as dual-funded channels, splices, payjoin and coinjoin. Each party should pay the charge of the inputs it adds, on top of its share of the net fee. Otherwise one party can add an old, large input whose charge exceeds the fee the others agreed to, and the transaction cannot confirm. Protocols that build such transactions should carry each input's confirmation height, so that the other parties can check the amount.
- **Mining interfaces.** Stratum V2 and Bitcoin Core's IPC mining interface need what `getblocktemplate` gives: the claim transaction, each transaction's charge, and the contribution as a coinbase output the client must include. Their fields are left to those protocols' specifications.

# Rationale

## Why the charge is levied at spend time

A soft fork cannot reduce the value of an output that is not being spent. Old nodes would still accept a later transaction that spends it at full value. The only point at which a soft fork can collect demurrage is when an output is spent. The block that spends it can be required to pay the charge, out of fees and subsidy that the block already controls.

The charge equals the decay accrued since the output was created. Up to rounding and fees, its total is the same whether a holder spends once after ten years or many times within that period. In both cases a holder pays the decay of the index over the time it held the coins. The timing of a spend therefore neither avoids nor brings forward any demurrage. It does decide when miners are paid (see Realised budget).

## Why the block pays, not each transaction

Peter Todd's 2022 sketch has each transaction contain an output that pays its demurrage to the pool. This BIP makes the block responsible instead, and the coinbase pays the block's charges in one output.

- **No transaction becomes invalid.** A transaction that had to carry its own charge would become invalid as soon as the charge, which grows each block, exceeded the amount it had set aside. That is the pre-signed transaction failure that led BIP 462 to add a reference height. Here a transaction is valid if and only if it was valid before this BIP, unless it creates or spends an output with `POOL_SCRIPT`. A transaction that pays too little only becomes uneconomic to mine. Anyone who can spend one of its outputs can then bump it with a child (CPFP), and anyone can pay a miner directly.
- **No new field.** No reference height is needed, because validity does not depend on the charge. The transaction format, signature hashes, PSBT and parsers are unchanged.
- **Less block space and UTXO growth.** One output per block replaces one per transaction, and the claim transaction has at most two inputs.

## Why a pool, rather than paying the includer

If the charge were simply a required fee paid to the miner that includes the transaction:

- a miner spending its own coins in its own blocks would pay its charges to itself;
- any holder could have a miner include its transaction and refund most of the charge out of band, so charges would be bargained away;
- a long-idle output moving would hand one block a large windfall, the reorganisation incentive that Carlsten et al. (2016) describe and that Todd cites against fee-only security.

With a pool, the miner that includes a transaction receives none of its charge directly. A party with hashrate share `h_share` recovers only about `h_share` of any charge through future payouts. Self-dealing and refunds therefore recover at most that share. The charge is computed from the outputs spent, not from any amount that users or miners choose, so the pool's inflow cannot be routed around. The only way to avoid it is not to spend.

## Why the pool is held in outputs

Old nodes reject any coinbase that claims more than subsidy plus fees. Value set aside for future miners must therefore stay visible to old nodes as ordinary outputs, and come back to miners as fees. `POOL_SCRIPT` is a script that old nodes treat as spendable by anyone. This BIP restricts its spending to the claim transaction, as segwit and taproot restricted outputs that old nodes treated the same way.

`POOL_SCRIPT` is a bare non-standard script, not an undefined witness program, because of relay. Current policy relays transactions that create outputs to undefined witness programs, and refuses only transactions that spend them. Had the pool used one, anyone could broadcast a cheap transaction creating a pool output after activation, and non-upgraded nodes would relay it to non-upgraded miners, whose blocks would then be invalid. Current policy refuses both to create and to spend a non-standard script (`scriptpubkey`, `bad-txns-nonstandard-inputs`). Non-upgraded nodes therefore relay neither a transaction that would break this BIP's rules nor one that would take the pool.

Contributions are coinbase outputs, so the existing 100-block maturity rule delays each one by about 17 hours before it joins the pool. This is the only constraint the maturity rule imposes.

## Why a deterministic claim transaction at index 1

The claim transaction's inputs, output and amounts are fully determined by the chain. It needs no signature, cannot be malleated and has the same txid in every block template. Fixing its position makes it easy to find and validate. Making it mandatory keeps the pool in a single carry output plus at most 100 immature contributions, and makes the payout of every block a function of the chain alone. The claim transaction is 67 or 108 bytes and the contribution 16 bytes, about 0.012% of a block. Neither size is 64 bytes, so the claim transaction does not conflict with the rule against 64-byte transactions in BIP 54.

## Why fees do not count towards the target

Like BIP 462 since its draft 0.5.0, this BIP pays fees to the block producer and ignores them when setting the rate. If fees counted towards the target, a miner that paid itself a large fee could lower the next rate. Pooling fees prevents that, but removes the miner's marginal reward for including transactions and gives users and miners a reason to move fees out of the measured channel (see BIP 462's rationale). With fees left out, nothing in the rate can be manipulated, and miners keep the full incentive to include transactions.

The cost is that holders pay the shortfall against the subsidy even when fees are high. Fees still add to the budget: a miner's revenue is subsidy, net fees and pool payouts.

Lowering charges after deployment, for example to count fees, would relax a rule, which is a hard fork. Whether fees should count must therefore be settled before deployment. Counting the median per-block fee is the most robust option if they must.

## Why the target uses scheduled supply

BIP 462 measures effective supply by maintaining the effective value of the UTXO set, which needs a normalised total, 256-bit arithmetic and a one-time scan of the UTXO set. Here effective value matters only at spend time, and the target is a rate, so the scheduled supply serves as well. It also makes the rate a pure function of height.

## Why the rate does not chase the realised budget

Three changes could bring the realised budget closer to the target. This draft adopts none of them.

- **A higher target**, by a fixed factor, to allow for supply that never moves and for the lag. It keeps the rate a function of height. The factor has to be chosen decades ahead, and holders who spend pay for those who never do.
- **A feedback term** that raises the rate when the contributions of earlier periods fall short. The rate would no longer be known in advance. The lag between accrual and payment is years long, so the correction would overshoot: it would raise the rate while outstanding charges build up, and the budget would exceed the target when they are finally paid. What holders spend, and which spends miners include, would also move the rate. The fixed schedule rules that out.
- **A surcharge that grows with an output's age**, so that deferring costs something. It would bring charges forward. It would also make the charge depend on how often an output is re-spent, make holders move coins in cold storage on a schedule, and add to what a pre-signed transaction owes.

Raising the rate later is a soft fork, and lowering it is a hard fork (see Security Considerations). This draft therefore keeps the lower, fixed schedule and states what it delivers. The choice should be made with a simulation over the real age distribution of unspent outputs (see Open Questions).

## Why two deployments

Once charges begin, nearly every block needs a contribution and a claim transaction. Two things must then be true of nearly all hashrate: its nodes enforce the rules, and its block-building software produces the new structure. One signal cannot show both without forcing miners to upgrade both at once (see getblocktemplate). With a single deployment that nodes signal alone, nothing shows whether pools are ready for the first charge. Those that are not would have their templates refused at that height, or would build invalid blocks from templates of their own.

The second deployment makes the first charge wait for that evidence. Miners are the ones who receive the charges, so once they are ready they have no reason to withhold the signal. The cost is that the start of charges is no longer fixed by the first deployment: if `demurrage_charges` activates after height 1,260,000, the decay before `CHARGE_HEIGHT` is skipped.

## Why POOL_DIVISOR is 10,000

Charges arrive when outputs move, not when they decay, so the inflow to the pool is irregular. For example, a 100,000 BTC output that is idle from 2032 and spent at the 2044 halving owes about 2,190 BTC. That is about two weeks of the average flow of charges at that time, if every output paid. With a divisor of 1,000, it would at first add about 2.2 BTC to every block's payout, twice that average flow, halving every five days. With 10,000, it adds about 0.22 BTC per block, halving every 48 days.

A longer half-life smooths more but holds more value in the pool: about `POOL_DIVISOR` blocks of inflow. That is around 12,000 BTC once the subsidy has ended, if every output paid. The value is provisional.

## BIP 462's objections to spend-time demurrage

BIP 462 lists spend-time demurrage among its alternatives, and names two costs:

- **Revenue arrives in large irregular amounts when long-idle coins move, unless it is smoothed through a pool.** This BIP has that pool. It spreads every charge over months (a half-life of about 48 days), and the including miner receives none of it directly. A block that spends a long-idle output is worth no more to reorganise than any other.
- **Lost coins never pay.** True, and unavoidable in a soft fork. See Security Considerations.

There is a third cost. The revenue is late as well as irregular: a charge is paid only when its output is spent, which can be years after it accrued (see Realised budget). The pool does not help with that.

## Relationship to tail emission

As in BIP 462, demurrage and tail emission are economically equivalent at equal rates, apart from the unit of account. This BIP keeps the 21,000,000 BTC schedule in nominal terms as well. Its rate is bounded by the target, zero while the subsidy covers the target, and fixed in advance.

## Alternatives considered

- **Per-transaction pool outputs** (Todd, 2022). Pre-signed transactions would become invalid once their charge grew, each transaction would carry an extra output, and claims would have to sweep thousands of outputs per block.
- **Charge paid to the includer.** Self-dealing, out-of-band refunds and large single-block windfalls, as above.
- **An inherited or committed reference height**, for example in `nLockTime`, so that a transaction could defer decay to its outputs. A holder could then defer its charge indefinitely, and the charge would fall on whoever eventually combined the output with a younger one. A block-level charge needs no reference height.
- **Burning the charge.** It would fund no one. Security needs payments to miners.
- **Recycling lost coins.** It would require spending outputs without their owners' signatures. Old nodes would reject that, so it is a hard fork.
- **Continuous demurrage (BIP 462) and tail emission.** Both are hard forks.

# Backward Compatibility

This is a **soft fork**. Every rule restricts blocks that old nodes accept. Nodes that do not upgrade follow the most-work chain, see pool outputs as anyone-can-spend outputs, and relay neither payments to them nor spends of them. Unlike segwit and taproot, however, this BIP requires new structure in nearly every block once charges begin (see Miners, below, and Security Considerations).

- **Transactions.** No transaction that can be signed today becomes invalid, except one that creates or spends an output with `POOL_SCRIPT` after activation. The script is meant to be unused, which should be checked against the chain before deployment. Spending a `POOL_SCRIPT` output created before activation remains valid.
- **Pre-signed transactions** (timelocked inheritance and recovery transactions, vaults, channel commitments, transaction trees) all remain valid, including those signed before activation. Valid is not the same as confirmable, though. To confirm, they need a fee, their own or a child's, that covers their charge. For example, a 100 BTC transaction signed in 2030 and broadcast in 2045 owes about 2.5 BTC. Pre-signed transactions should therefore keep an output that a child can spend, such as an anchor.
- **Transactions that no child can bump.** A child cannot be built when every output is timelocked, or when the keys are offline or deleted: transaction trees signed with deleted keys, vault transactions whose outputs are all delayed, and a channel commitment without anchors, for the party that broadcasts it. The charge must then be paid to a miner out of band. That payment alone is not enough when the charge exceeds the subsidy and the other fees of the block, because the block's contribution is paid out of them. The miner must also add a transaction of its own that pays the difference as a fee. In the 2045 example the subsidy is under 0.1 BTC. Out-of-band payment favours large pools that run accelerator services, and this BIP adds no way to pay another transaction's charge through relay (see Open Questions). The rate is zero until 2032, which leaves years to re-sign or settle structures that have no such output.
- **Miners.** Until `CHARGE_HEIGHT`, and after it while the rate is zero, no block owes a charge, so blocks from non-upgraded miners stay valid. The exception is a block with a transaction that creates a `POOL_SCRIPT` output, which such a miner can only have received outside normal relay. From the first block with a non-zero rate, nearly every block must contain a contribution, and every block from 100 blocks later a claim transaction. A miner that has not upgraded by then produces invalid blocks, even empty ones. Mining software that uses `getblocktemplate` must support the `demurrage_charges` rule by then, when templates start requiring it (see getblocktemplate).
- **Nodes that do not upgrade** follow the chain, but less well. Block relay between two of them needs an extra round trip per block once claim transactions begin (see Relay and mining policy). The fees they see in blocks include charges, so their fee estimates rise and stop being a guide to what a transaction must pay.
- **Wallets** must add the charge to the fee when they spend, and should report effective balances. A wallet that has not upgraded creates transactions that are valid, but upgraded nodes do not relay them, and miners do not mine them, while their fee is below their charge plus the minimum relay fee. They can be fee-bumped. A wallet that sizes fees by feerate alone has to be told the amount, and its limits on fees may refuse it.
- **Fee estimates and displays.** A feerate computed from a fee includes the charge. Estimators, explorers and Lightning nodes that negotiate feerates with their peers must use net fees (see Fees and interfaces). An upgraded and a non-upgraded Lightning node can disagree about the feerate a commitment needs.
- **Hardware signers and PSBT.** The charge is not part of what a signer authorises: the fee it signs is still inputs less outputs. A wrong charge estimate can only make a transaction slow to confirm, not spend more than the signer approved. But the fee a signer shows now includes the charge, so a large fee is no longer a sign that something is wrong. Fees and interfaces specifies a PSBT field for the confirmation height, and a bound that a signer can apply without trusting it.
- **Transactions with inputs from several parties** need each party to cover the charge of its own inputs (see Fees and interfaces).
- **Explorers and indexers** need no parser changes. They should show each output's charge, and the pool outputs.
- **TRUC and P2A** (BIP 431, BIP 433) are unaffected.

# Layer 2 and Lightning Network Considerations

## Channels

A channel's funding output owes its charge when the closing or commitment transaction confirms, for the decay since the funding transaction confirmed. No change to channel scripts is needed.

- **Accrual.** The charge accrues on the whole funding output while the balances in the channel move. Splitting it by the balances at close would let a party hold a balance for a year, route it out through its other channels just before closing, and leave its peer the charge for that year. Implementations should instead accrue the charge in the channel state. At each state update, the increase in the funding output's charge since the previous update is deducted from the two balances, in proportion to what each was in the previous state, and set aside. Each party then pays the decay on what it held, for as long as it held it.
- **Cooperative close.** The closing transaction's fee covers the charge, out of the amount set aside. The decay since the last update is split in proportion to the balances.
- **Force close.** The commitment transaction's fee, or its anchor child, covers the charge. The schedule is known, so the charge for any confirmation height can be computed exactly when a state is signed. Implementations should put the amount set aside in the commitment's fee, with a pre-payment up to the signing height plus a horizon such as `to_self_delay`, deducted in the same proportion. Beyond the horizon, the party that broadcasts pays the remainder through the anchor. Idle channels can refresh the pre-payment with a state update. A zero-fee commitment (TRUC with P2A) cannot carry the amount in its fee. It can carry it in the value of its anchor output, which the child that pays the charge spends.

A party that refuses to close cooperatively can make the other pay the charge beyond the pre-paid horizon. That amount is bounded by the decay since the last state update. Accrual is a change to the channel protocol, not to channel scripts, and both peers must implement it.

## Second-stage and penalty transactions

HTLC-success, HTLC-timeout and penalty transactions spend commitment outputs that are at most a few weeks old, so their charges are small (see the table). Anchor channels already let the broadcaster add fees to HTLC transactions. Watchtowers should include the charge for the longest delay they cover in the fee of the penalty transactions they hold.

## Magnitude on Lightning timescales

Maximum charge, at the full target rate, on a 0.1 BTC (10,000,000 sat) channel. The rate is zero until 2032 and below the target until the subsidy ends.

| Funding output age | Blocks | Maximum charge | On 0.1 BTC |
|---|---|---|---|
| One day | 144 | 8.2 ppm | 82 sat |
| Two weeks | 2,016 | 115 ppm | 1,150 sat |
| One month | 4,380 | 250 ppm | 2,500 sat |
| Six months | 26,280 | 0.15% | 15,000 sat |
| One year | 52,560 | 0.30% | 30,000 sat |

## Other protocols

Splicing, channel factories, LN-Symmetry, statechains and transaction trees need no consensus support. An output's charge accrues on-chain, whoever holds it off-chain, and is paid when the output is spent. Off-chain transfers of an output (statechains, for example) should price in its accrued charge.

A system that holds outputs against claims of a fixed nominal amount, such as a peg, a wrapped coin, a custodial balance or a fund, owes the outstanding charge of those outputs. Its reserves should be counted at effective value. Counted at nominal value, it is short by the outstanding charge as soon as it has to spend its old outputs. Where the amounts paid out are fixed in transactions signed in advance, as in some bridges, the operator that fronts a payout bears the charge unless the protocol reimburses it. Such systems should pass the charge on to their users, as BIP 462 describes.

# Deployment

This BIP is deployed with two version bits deployments (BIP 9 or BIP 8) that use the same signalling period. Their parameters are not set at draft stage.

- **`demurrage`** starts enforcement. From `ACTIVATION_HEIGHT` nodes apply the rules of this BIP. Until `CHARGE_HEIGHT` no block owes a charge, so the only rules with any effect are the restrictions on `POOL_SCRIPT` outputs, which apply only to transactions that current nodes do not relay. Nodes signal for it whatever mining software uses them.
- **`demurrage_charges`** starts the index. A node signals for it only on behalf of mining software that declares the rule (see getblocktemplate). `CHARGE_HEIGHT` is the first height at which both deployments are active. Signalling for it should not begin before signalling for `demurrage` does.

On mainnet the rate is zero below height 1,260,000, so no block owes a charge until the 2032 halving, whenever the deployments activate. Activating `demurrage` well before then gives miners, pools, wallets and Lightning implementations years to upgrade before any charge is owed. If `demurrage_charges` is not active by height 1,260,000, charges begin at `CHARGE_HEIGHT` instead, at the rate then in force.

From the first charge, nearly every block must contain new structure (see Security Considerations). Both deployments should therefore require near-universal miner signalling, and neither should be forced without it, as BIP 8 with `LOT=true` would.

Unlike BIP 462, nodes need no preparation:

- the rate and the index depend only on height and `CHARGE_HEIGHT`;
- the charge needs only the confirmation height that every node already stores with each unspent output;
- the pool is in the UTXO set, so assumeutxo snapshots carry it. A node that loads one finds the carry and the immature contributions with one scan for `POOL_SCRIPT` (see Claim transaction).

# Security Considerations

**Soft-fork security of the pool.** To non-upgraded nodes, pool outputs are spendable by anyone. If a majority of hashrate stopped enforcing this BIP, it could take the pool, and non-upgraded nodes would follow that chain. Every segwit and taproot output relies on the same model. The pool holds about `POOL_DIVISOR` blocks of inflow, a small fraction of the value held in those outputs.

**Nodes and miners that have not upgraded.** In segwit and taproot, a non-upgraded miner's blocks stayed valid by default, because the transactions that could break the new rules were not relayed. Here, once charges begin, almost every block must contain a contribution and a claim transaction. Every block from a non-upgraded miner is then invalid. With 5% of hashrate not upgraded, as BIP 9's threshold allows, that is about seven invalid blocks a day. Non-upgraded full nodes and SPV clients would accept each of them and then reorganise when the valid chain overtakes it. One-confirmation payments to them could be double spent. Miners that build on headers before validating blocks could extend these splits, as in the July 2015 fork after BIP 66. Upgraded nodes do not shield their peers from such blocks. High-bandwidth compact block relay (BIP 152) forwards a block before validating it in full, so an upgraded node relays a lagging miner's block to its peers, and those that have not upgraded accept it. This is true of any soft fork, but in others such blocks are rare. Checking the claim transaction before relay (see Relay and mining policy) stops most of them. Before charges begin, effectively all hashrate must therefore enforce this BIP and be able to build its blocks. The two deployments are how that is established: signalling for `demurrage` shows that nodes enforce the rules, and signalling for `demurrage_charges` that block builders are ready. Neither should be forced without it. Whatever hashrate has not signalled when they lock in is still exposed.

**The target is not a floor.** The rate is set as if every output paid its decay as it accrued (see Realised budget). What miners receive lags that for as long as outstanding charges grow, which starts with the first charge and can last for years. The security this BIP buys in its first decades is therefore less than the rate table suggests. How much less depends on how old the outputs that move are, which should be estimated from the chain before deployment.

**Lost and never-spent coins.** A soft fork cannot charge an output that is never spent. Lost coins never pay, and neither do coins their holders never move. If a fraction `L` of supply is lost, the demurrage that miners receive converges to at most `(1 − L)` of the shortfall. The target could be raised to compensate, at the cost of charging active holders more (see Rationale).

**Revenue timing.** Charges arrive when outputs move rather than as they accrue. The pool spreads them over months, but the budget in any period still depends on how much old value moved in the months before. Large holders who coordinate when they move could make it lumpier; the pool limits the effect.

**Deferral, custody and repeal.** Deferring a charge costs nothing: an output owes the same decay whether it is spent now or later. A holder that expects a later change of rules to lower or remove the charge gains by not spending. A custodian, exchange, fund or peg that pays withdrawals from its newest outputs can leave its oldest ones unspent for as long as deposits keep pace with withdrawals. Its users can then pay each other, and withdraw, without the charge on those outputs ever being paid, while someone who holds their own keys pays the charge whenever they spend. This favours custody, and delays the budget further. Lowering the rate or removing the charge relaxes a rule, so it would need a hard fork. Raising the rate would be a soft fork. Once deployed, the charge is easier to raise than to lower.

**Block rate.** The index falls, and the pool pays out, per block. If blocks arrive faster than one every ten minutes, holders pay more per year than the rate table shows. A majority of hashrate that lowered the difficulty by manipulating timestamps (the timewarp attack) would collect charges and payouts faster. That incentive exists for the subsidy today and fades with it. Under this BIP it does not fade. This BIP therefore depends on the timewarp fix in BIP 54.

**Consent.** A soft fork binds nodes that do not upgrade: their owners' coins owe the charge whether or not they agree. Being deployable as a soft fork does not reduce the consensus this BIP needs. Users who reject it can avoid it only by forking away.

**Self-dealing and inclusion.** The pool's inflow is fixed by the outputs spent, so neither miners nor users can change it by choosing fees. A miner spending its own coins pays the full charge into the pool and recovers its hashrate share of it over time. Fees go to the includer, so the marginal reward for including a transaction is its full net fee.

**Capital flight and perceived confiscation.** As in BIP 462. A carrying cost competes against substitutes without one, and holders see their effective balances fall whenever the rate is non-zero.

**Implementation determinism.** The rate, the index, the charge and the claim transaction must be computed identically by all implementations, using integer arithmetic.

**Privacy.** Unchanged. The charge depends only on data already public: an output's value and its confirmation height.

# Reference Implementation

The Bitcoin Core branch `bip462b-softfork-demurrage` implements this version of the BIP, with the differences listed below. It covers the consensus rules, the relay and mining policy, block assembly, `getblocktemplate`, compact block relay, assumeutxo snapshots, node interfaces, the PSBT field, the wallet, fee estimation, unit tests and three functional tests. Its two deployments, `demurrage` and `demurrage_charges`, are `NEVER_ACTIVE` on every network. On regtest each can be activated at a fixed height with `-testactivationheight=<deployment>@<height>`, or through signalling with `-vbparams`. In the main functional test, a node that does not enforce the rules accepts every block that an enforcing node accepts.

The consensus changes are:

- the rate and the index, as in BIP 462 but computed from height alone;
- the block charge, in `ConnectBlock`, from the confirmation heights already stored in the UTXO set;
- the contribution, pool output and claim transaction checks.

Charges enter the mempool as a negative fee delta, like `prioritisetransaction`, but one that is not saved with the mempool. Cluster linearisation, block assembly, package relay and trimming then rank by net fee without further changes. Each mempool entry keeps its evaluation height, its policy charge, its policy charge at acceptance, and the value and confirmation height of each input.

None of BIP 462's reference heights, UTXO format change, UTXO set value or coinbase dividend code is needed. The node keeps each block's two pool outpoints with its block index, 72 bytes a block, so a pruned node finds a block's pool inputs without the blocks that created them.

Templates have the `charge` and `demurrage_contribution` fields. The IPC mining interface gives the contribution as a required coinbase output.

The other parts of this BIP are implemented as follows:

- **Compact blocks.** A node prefills the claim transaction in the compact blocks it sends, checks it before it announces a block, and builds it for a block it receives without it. For a block whose parent is not its tip, it reads the carry from the parent block.
- **Snapshots.** A node that loads an assumeutxo snapshot finds the carry and the unspent contributions among the snapshot's coins, and records them as the pool outputs of the base block and of the 99 blocks below it.
- **Node interfaces.** The mempool RPCs, `testmempoolaccept` and `submitpackage` report each transaction's evaluation height, policy charge and net fee. `getrawtransaction` and `getblock` report the charge and net fee of a confirmed transaction. `gettxout`, `scantxoutset` and the REST interface report an output's charge in the next block and its effective value. The fee limits of `sendrawtransaction` and `testmempoolaccept` apply to the net fee.
- **PSBT.** The field has the provisional type `0x20`. The wallet and `utxoupdatepsbt` fill it. `analyzepsbt` gives the charge that the stated heights imply, the net fee, and the bound that does not depend on them.
- **Wallet.** Coin selection counts each input's charge as part of the cost of spending it. A transaction pays its feerate on its size and, on top, the greater of its policy charge and its charge six blocks after the next block. Fee bumps and the wallet's fee limits compare net fees. The wallet reports each output's charge and effective value, an effective balance, and the charge and net fee of each transaction it sent.
- **Fee estimation** tracks each transaction's net feerate when it entered the mempool.

It differs from this version as follows:

- the PSBT field's type is not assigned;
- the graphical interface shows a transaction's fee without separating the charge.

The bound for signers that cannot check a height is computed by `analyzepsbt`. Applying it is left to software that checks a fee before it signs, which the wallet does not do for a PSBT.

# Open Questions

- **`POOL_SCRIPT`.** It must be a script that current policy refuses both to create and to spend, which rules out undefined witness programs and P2A. Whether the script is unused should be checked against the chain.
- **Lagging miners.** Whether making the claim transaction optional is worth its complexity. Only blocks that spend no older output, in practice empty blocks, would then stay valid when a non-upgraded miner builds them. The risk to non-upgraded nodes would barely change.
- **`POOL_DIVISOR`.** The value trades smoothing against the size of the pool. It should be calibrated against realistic patterns of old outputs moving.
- **The target.** Whether to bring the realised budget closer to the target with a higher target, a feedback term or an age surcharge (see Rationale). The answer needs a simulation over the real age distribution of unspent outputs, including the value that never moves.
- **Fees.** Whether fees should count towards the target, through a median per-block fee, before deployment rather than after.
- **Fee sponsorship.** A rule that made a transaction valid only in a block that also contains another transaction it names would let anyone pay a stuck transaction's charge through ordinary relay, which otherwise needs an arrangement with a miner. It would also make one transaction's validity depend on another's. A sponsor would be lost if its target confirmed without it, including after a reorganisation, and so would anything that spent the sponsor's outputs. Anyone could attach a sponsor to anyone's transaction, which relay policy would have to bound. Whether this BIP should include such a rule, or depend on a separate one, is open.
- **`CHARGE_TOLERANCE` and `CHARGE_MARGIN`.** Both values are provisional. A lower tolerance costs spenders less and re-evaluates more transactions each block. They should be set from measurements on a full mempool.
- **A minimum margin.** An input whose charge grows by more than `CHARGE_TOLERANCE` a block has no margin: about 175 BTC at the full target rate. A transaction that spends one and pays the minimum relay feerate falls below that feerate a block later. A child that spends such an output of an unconfirmed transaction is charged nothing until its parent confirms without it. Each then waits for a bump. Evaluating every transaction at least a few blocks ahead would avoid this. Six blocks would overstate the charge of a 1,000 BTC input by about 34,000 satoshis. Whether that is worth a third policy parameter is open. Until it is settled, a wallet has to add the margin itself, as the reference implementation's does. That margin is net fee when the transaction is accepted, so the replacement rule counts it: a replacement pays the margin of the transaction it replaces as well as its own.
- **Interfaces.** Fields for Stratum V2 and the IPC mining interface, and the type of the PSBT field.

The mechanism is Peter Todd's: a demurrage charged at spend time and paid into a pool of future mining fees, deployable as a soft fork. Errors in this specification of it are the author's.

# Changelog

- **0.4.2** (2026-11-24): The reference implementation also builds the claim transaction of a compact block whose parent is not its tip, and reports charges for confirmed transactions and in the wallet's transaction lists. No rule or recommendation has changed.
- **0.4.1** (2026-11-24): The reference implementation now covers compact block reconstruction, assumeutxo snapshots, the PSBT field, the remaining node interfaces, the wallet and fee estimation. No rule or recommendation has changed. Implementing the wallet showed that a margin added by a wallet raises the cost of replacing its transactions, which is noted under Open Questions.
- **0.4.0** (2026-11-22): Changes prompted by a review of 0.3.1 and of the reference implementation. The consensus rules are unchanged when both deployments activate together.
  - The 0.30% is described as a target and an upper bound, not a floor. Added Realised budget, which defines the outstanding charge and what miners receive, and the rationale for not raising the rate to make up the difference.
  - Two deployments. `demurrage` starts enforcement at `ACTIVATION_HEIGHT`. `demurrage_charges`, which nodes signal only for mining software that declares it, starts the index at `CHARGE_HEIGHT`.
  - Policy charges are evaluated per transaction, up to `CHARGE_MARGIN` blocks ahead but overstated by at most `CHARGE_TOLERANCE`, in place of one evaluation height 144 to 287 blocks ahead for the whole mempool.
  - Replacement compares against a replaced transaction's net fee at acceptance when that is higher. Block assembly leaves out a transaction whose charge the block cannot fund.
  - Added Fees and interfaces: node interfaces, a PSBT field, a bound for signers, and transactions with inputs from several parties.
  - Backward Compatibility covers transactions that no child can bump, out-of-band payment when the charge exceeds the block's reward, non-upgraded nodes, and fee estimates.
  - Lightning channels accrue the charge in the channel state. Systems with fixed nominal claims count reserves at effective value.
  - Compact block relay between non-upgraded nodes, the timewarp incentive, and deferral by custodians are stated. Nodes that prune should keep the pool inputs as chain state.
  - The comparison with BIP 462 follows its draft 0.5.0, which has no fee pool and no transaction field.
  - The reference implementation follows this version, except for the differences its section lists. Implementing it showed that large inputs have no margin, which is now an open question.
- **0.3.1** (2026-11-22): The reference implementation's `getblocktemplate` now follows 0.3.0.
- **0.3.0** (2026-11-22): `getblocktemplate` lists the `demurrage` rule as optional from activation and as required from the first rate period with a non-zero rate, rather than as required from activation. Nodes signal whether or not the client supports the rule, and warn clients that do not.
- **0.2.0** (2026-11-22): Changes prompted by the reference implementation. There is no change to the consensus rules on mainnet.
  - `RATE_PERIOD` is the deployment's signalling period, and the target is a parameter, with values for regtest.
  - Specified the policy charge of inputs that spend unconfirmed outputs, and charges before activation.
  - Recomputing charges does not evict transactions.
  - Fee rules such as ephemeral dust compare the fee, not the net fee.
  - Specified `getblocktemplate` support.
  - Stated how to find the pool inputs in the UTXO set.
  - Compact block relay should prefill the claim transaction and check it before relay.
  - Defined the annual rate in the rate table.
  - Added test vectors and noted BIP 54.
