# Abstract

This BIP proposes a **security budget floor** for Bitcoin. For each block, the protocol compares the block subsidy with a target of **0.30% of effective supply per year**. Any shortfall is made up by a **demurrage**: a small carrying cost levied on every unspent transaction output (UTXO) and paid to the block's miner. When the subsidy meets the target, the demurrage rate is zero. Transaction fees are paid to the miner that includes them, as today, on top of the floor.

Because today's subsidy exceeds the target, demurrage would not apply until the 2032 halving. It then phases in as the subsidy halves, so that subsidy plus demurrage hold the security budget at the target. The rate depends only on the subsidy schedule and the value of the UTXO set, so it cannot be manipulated with fees and can be anticipated years in advance. Effective supply follows the existing issuance schedule and never exceeds 21,000,000 BTC.

Existing transactions do not change. Every output inherits a **reference height** from the outputs its transaction spends, and a transaction's inputs are valued at that height. A transaction's validity therefore does not depend on when it is mined, so pre-signed transactions, including those signed before activation, remain valid. Each block commits to the demurrage state and to its transactions' reference heights, so that light clients can verify values, and an optional signature hash flag lets a signer commit to the values of the inputs it spends.

# Motivation

Bitcoin's security model relies on two miner revenue streams: the block subsidy and transaction fees. The subsidy halves approximately every four years and trends to zero around 2140, so long-term security depends on fees replacing it.

There is credible doubt that they will. In 2026, fees fell to between 0.5% and 0.7% of miner revenue while daily transaction counts reached record levels. Fees are priced by competition for block space, which is not currently scarce. Neither the volume of activity nor the value being secured enters that price. Bitcoin is also predominantly held rather than spent, and holding pays nothing towards security.

Budish (2018) shows that for majority attacks to remain unprofitable, the recurring payments to miners (a flow) must remain large relative to the value an attack could capture or destroy (a stock). A subsidy that halves towards zero moves in the opposite direction as Bitcoin's value grows.

The widely discussed remedies each break a core property: tail issuance abandons the 21,000,000 BTC schedule, and proof-of-stake abandons proof-of-work. A fixed-rate demurrage preserves both but charges holders from the start, while the subsidy alone still exceeds any plausible security target.

This proposal sets a floor instead. It charges holders only for the part of the security budget that the subsidy no longer covers, phasing in as the subsidy halves. Fees remain an incentive on top of the floor.

# Specification

## Overview

1. A global **demurrage index** tracks cumulative decay since activation. Each UTXO has a reference height, and its effective (spendable) value is its nominal value scaled by the fall in the index since that height.
2. The demurrage rate of each block is set from the shortfall between a target budget and that block's subsidy. The rate is between zero and the target rate.
3. Each block's miner may claim a **demurrage dividend** equal to the decay accrued across the UTXO set during that block.
4. Transaction fees are paid to the miner of the block that includes them, as today. They do not count towards the target.
5. Every output **inherits a reference height** from the outputs its transaction spends, and inputs are valued at it, so a transaction's validity does not depend on when it is mined.
6. Each block's coinbase **commits** to the demurrage state and to the reference height of each of the block's transactions.
7. An optional signature hash flag, `SIGHASH_DEMURRAGE`, commits a taproot signature to the values of the transaction's inputs. Such a signature is invalid on a chain that does not apply this BIP.

## Parameters

```
TARGET_RATE_ANNUAL      = 0.0030             (0.30% of effective supply per year)
BLOCKS_PER_YEAR         = 52,560             (≈ 144 blocks/day)
TARGET_RATE_PER_BLOCK   = TARGET_RATE_ANNUAL / BLOCKS_PER_YEAR
                        = 3 / 52,560,000     (≈ 5.708e-8)
INDEX_ONE               = 10^18              (fixed-point scale of the index and the rate)
INDEX_MIN               = 10^9               (index at or below which demurrage stops)
SIGHASH_DEMURRAGE       = 0x40               (signature hash flag)
COMMITMENT_HEADER       = 0x9996b0b3         (first four bytes of SHA256("BIP462"))
ACTIVATION_HEIGHT       = [to be set; see Deployment]
```

All parameters are consensus constants. None is adjustable by miners, nodes, or any governance process.

The rate accrues per block, not per unit of time. `BLOCKS_PER_YEAR` is the nominal figure that converts the annual target into a per-block rate. The charge over a calendar year follows the number of blocks actually produced (see Block timestamps).

## Fixed-point arithmetic

All arithmetic is performed on integers. Floating-point arithmetic must not be used.

- Amounts are integers in satoshis.
- The demurrage index `I(h)` and the per-block rate `r(h)` are integers scaled by `INDEX_ONE`: an index of `INDEX_ONE` means 1.0, and a rate of 57,077,625,570 means about 5.708e-8 per block.
- Every division rounds down (`floor`). Intermediate products must be computed exactly; they need up to 256 bits.

The test vectors give the expected result of the formulas they cover (see Test Vectors).

## Demurrage rate

For each block at height `h ≥ ACTIVATION_HEIGHT`, with `U = U(h − 1)` the effective value of the UTXO set after the block's parent (see UTXO set value):

```
target(h)     = floor(U × 3 / 52,560,000)                 (TARGET_RATE_PER_BLOCK × U)
shortfall(h)  = max(0, target(h) − block_subsidy(h))
r(h)          = floor(shortfall(h) × INDEX_ONE / U)       (r(h) = 0 if U = 0 or I(h − 1) ≤ INDEX_MIN)
```

where `block_subsidy(h)` is the amount the halving schedule entitles block `h` to, whatever its coinbase actually claims.

By construction `0 ≤ r(h) ≤ floor(INDEX_ONE × 3 / 52,560,000) = 57,077,625,570`, the target rate. The rate of a block depends only on the subsidy schedule and on `U(h − 1)`. It is therefore fully determined once the block's parent is known, and never depends on the contents of the block itself.

## Demurrage index

Maintain a cumulative index `I(h)` with `I(h) = INDEX_ONE` (1.0) for every `h < ACTIVATION_HEIGHT` and, for each block `h ≥ ACTIVATION_HEIGHT`:

```
I(h) = floor(I(h−1) × (INDEX_ONE − r(h)) / INDEX_ONE)
```

The index is non-increasing and deterministic. Its value at any past height is known to every node.

Once the index is at or below `INDEX_MIN`, the rate is zero and the index stops falling. The index therefore never reaches zero, and every division by an index is defined. At the full target rate the index reaches `INDEX_MIN` about 6,900 years after activation (see Why the index has a floor).

## Reference heights

Every output has a **reference height**:

- the reference height of a coinbase output is the height of the block that includes it;
- the reference height of any other output is the reference height of the transaction that created it;
- the reference height of a transaction is the highest reference height among the outputs it spends.

The rules apply to every transaction, before and after activation, and need no new transaction field. Since `I(h) = INDEX_ONE` for every `h < ACTIVATION_HEIGHT`, all reference heights below `ACTIVATION_HEIGHT` are equivalent. Implementations may therefore record any height below `ACTIVATION_HEIGHT` for an output created before activation, for example its own height.

Where a reference height is committed to (see Demurrage commitment and Signature hash flag), it is written in **committed form**: a reference height below `ACTIVATION_HEIGHT` is written as `ACTIVATION_HEIGHT − 1`. The commitments therefore do not depend on which height an implementation records for an output created before activation.

Every reference height descends from a coinbase output that was mature when spent, so a transaction's reference height is at least `COINBASE_MATURITY` (100) blocks below the height of the block that includes it. The index at a transaction's reference height is therefore always known, and unchanged by any reorganisation less than 100 blocks deep.

An output's `I_created` is `I(reference height)`. The effective value of an output with nominal value `v` at height `h` is:

```
effective_value(h) = floor(v × I(h) / I_created)
```

Rounding down discards less than one satoshi each time an output is valued. These remainders are not credited to anyone. See Supply accounting.

## Transaction valuation

A transaction's inputs are valued at the index of its reference height:

```
input_value = floor(v × I(tx.ref_height) / I_created)
```

The transaction is valid if the sum of its output values does not exceed the sum of its input values. Its fee is `fee(tx) = sum(input_value) − sum(output values)`. All of a transaction's amounts, including its fee, are therefore expressed at the index of its reference height.

Every other rule on transactions is unchanged: their serialization, their existing signature hashes, and the range checks on output values. One optional signature hash flag is added (see Signature hash flag).

The reference height is value-neutral. Inputs valued at a later reference height are worth less, but the outputs they fund are created at the same lower index, so the effective value delivered is unchanged. Only the unit in which the nominal amounts are written differs. In particular:

- a transaction with a single input is always valued at that input's nominal value;
- a transaction that spends only outputs created before activation is valued at index 1.0, however long after activation it is mined.

## UTXO set value

`U(h)`, the effective value of the UTXO set after block `h`, is defined through the UTXO set's normalized total `N(h)`, so that it can be maintained incrementally:

```
n(o)  = floor(v × INDEX_ONE² / I_created)        (normalized value of an unspent output o)
N(h)  = sum of n(o) over the UTXO set after block h
U(h)  = floor(N(h) × I(h) / INDEX_ONE²)
```

`N` changes only when outputs are created or spent: each block adds `n(o)` for every output it adds to the UTXO set, and subtracts `n(o)` for every output it spends. Outputs that are never added to the UTXO set, such as provably unspendable `OP_RETURN` outputs, do not count.

`U(h)` is not the sum of each output's rounded effective value. Such a sum would have to be recomputed over the whole UTXO set every block, because every output's rounding changes as the index falls.

At `ACTIVATION_HEIGHT − 1`, every output has `I_created = INDEX_ONE`, so `N = INDEX_ONE × (total value of the UTXO set)`. An implementation needs that total once. It should not wait until its chain reaches `ACTIVATION_HEIGHT − 1` to compute it: scanning the whole UTXO set at that moment would stall every node and miner at the same block. It can scan the UTXO set at any earlier height and then keep the total current, adding the value of the outputs each block creates and subtracting the value of those it spends.

## Coinbase

For each block at height `h ≥ ACTIVATION_HEIGHT`, the miner may claim:

```
demurrage_dividend(h) = floor(r(h) × U(h−1) / INDEX_ONE)
fee_effective(tx, h)  = floor(fee(tx) × I(h) / I(tx.ref_height))
```

The dividend is the block's shortfall, less at most one satoshi of rounding. `fee_effective` converts each fee from the index of its transaction's reference height to the index of the block, at which the coinbase's outputs are created.

Consensus rule: a block is invalid if its coinbase output value exceeds:

```
block_subsidy(h) + sum of fee_effective(tx, h) over the block's transactions + demurrage_dividend(h)
```

The limit depends on the chain state, so it is checked when the block is connected to the chain, not in context-free block checks. Any part of the limit that the coinbase does not claim is destroyed.

## Demurrage commitment

The coinbase transaction of every block at height `h ≥ ACTIVATION_HEIGHT` must contain an output whose `scriptPubKey` is at least 38 bytes long and begins with the 6 bytes `0x6a249996b0b3`: `OP_RETURN`, a push of 36 bytes, and `COMMITMENT_HEADER`. The 32 bytes that follow are the commitment. If more than one output matches, the one with the highest index is used, as for the witness commitment of BIP 141.

```
state(h)         = I(h) (8 bytes) || r(h) (8 bytes) || N(h − 1) (32 bytes)        (little-endian)
leaf(tx)         = SHA256d(txid || reference height of tx (4 bytes, little-endian, committed form))
ref_height_root  = Merkle root of the leaves of the block's transactions, in block order
commitment(h)    = SHA256d(state(h) || ref_height_root)
```

`SHA256d` is double SHA256, and the Merkle root is computed as the block's transaction Merkle root is. The coinbase's leaf uses 32 zero bytes in place of its txid, and `h` as its reference height. A block whose commitment does not match these values is invalid.

The commitment depends only on the state after the block's parent and on the block's transactions, as the witness commitment does, so it can be computed before the coinbase is complete. `N(h)` is committed by the next block.

## Signature hash flag

From `ACTIVATION_HEIGHT`, the common signature message of BIP 341, which BIP 342 shares, accepts three more `hash_type` values: `0x41`, `0x42` and `0x43`. They are `SIGHASH_ALL`, `SIGHASH_NONE` and `SIGHASH_SINGLE` combined with `SIGHASH_DEMURRAGE`. For these values, `SigMsg` is computed as for `hash_type & 0x3f`, except that:

- its first byte is the full `hash_type`;
- two fields follow `sha_sequences`:
  - `sha_input_values` (32): the SHA256 of the serialization of the values of all inputs, 8 bytes each, where the value of an input is the one that Transaction valuation defines: its value at the index of the transaction's reference height;
  - `ref_height` (4): the transaction's reference height, in committed form.

The maximum length of `SigMsg` becomes 242 bytes. `SIGHASH_DEMURRAGE` cannot be combined with `SIGHASH_ANYONECANPAY`, which leaves the other inputs, and therefore the transaction's reference height, open. Legacy and BIP 143 signature hashes do not change.

The flag is optional. A signature that uses it is valid only if the signer was given the true value of every input, so a signer that adds up the values it signed for, and subtracts the outputs, knows the transaction's fee exactly. Such a signature is invalid on any chain that does not apply this BIP, where these `hash_type` values are undefined.

## Block timestamps

From `ACTIVATION_HEIGHT`, the two timestamp rules of BIP 54 apply to every block, whether or not BIP 54 is otherwise in force. For a block at height `n` with timestamp `T(n)`:

- if `n mod 2016 = 0`, then `T(n) ≥ T(n − 1) − 7200`;
- if `n mod 2016 = 2015`, then `T(n) ≥ T(n − 2015)`.

These rules close the timewarp attack, which would otherwise let a majority of hashrate lower the difficulty at will and collect the per-block dividend far more often than once per ten minutes (see Why the timestamp rules).

## Activation block

The block at `ACTIVATION_HEIGHT` must have the highest bit (bit 31) of its header version set. The existing rule that rejects header versions below 4 does not apply to that block. It applies unchanged to every other block, so no other block can have the bit set.

Read as a signed integer, such a version is negative. Every node that does not apply this BIP therefore rejects the block, and every node that applies it rejects a block at that height without the bit. The two rule sets separate at `ACTIVATION_HEIGHT`, not at the first block whose coinbase claims a dividend (see Why an activation marker).

## Supply accounting

The demurrage dividend is minted at face value in the coinbase while existing outputs keep their nominal values. The sum of nominal UTXO values therefore grows over time. Nominal values have no economic meaning after activation; wallets, exchanges and indexers must report effective values.

**Effective supply**, the effective value of the UTXO set, is conserved by demurrage and by fees: what holders lose to decay, miners receive as dividend, and fees move from inputs to the coinbase. Effective supply changes only through the block subsidy, so it follows the existing issuance schedule and never exceeds 21,000,000 BTC.

Conservation holds up to rounding down. Each block can lose up to about one satoshi per input it spends and per transaction it includes, plus a few satoshis from the dividend and the UTXO set value, and it never gains. A coinbase that claims less than its limit also reduces effective supply.

An output's nominal value is its effective value at the index of its reference height. It exceeds the output's current effective value by the factor `I(ref_height) / I(now)`: at most 0.3% per year of the output's age in reference height. The existing limit of 21,000,000 BTC on each output's nominal value therefore binds only an output that holds nearly the entire supply with a reference height many decades old. Spending a recent output alongside it raises the transaction's reference height, and so lowers the nominal amounts.

## Interaction with the existing subsidy

The halving schedule is unchanged. The subsidy counts towards the target, so while the subsidy alone exceeds the target the demurrage rate is zero. As halvings reduce the subsidy, demurrage phases in automatically. Each block pays its miner `max(target(h), block_subsidy(h))`, less at most one satoshi of rounding, plus fees. The rate follows each halving in the same block, and no special handling is required at any halving or when the subsidy reaches zero.

# Rationale

## Why a target net of the subsidy

A fixed rate charges holders from activation, while the subsidy alone already exceeds the target. A target net of the subsidy charges nothing until the subsidy falls below the target, then phases in with each halving, so that subsidy plus demurrage hold the security budget at the target.

The target is expressed as a fraction of effective supply in BTC, and the subsidy is fixed in BTC. The rate can therefore be computed by every node without a price oracle. A target expressed in fiat terms would require a price feed that cannot be obtained trustlessly.

Because the rate depends only on the subsidy schedule and the value of the UTXO set, holders can anticipate it years ahead, and no participant can change it except by destroying coins (see Security Considerations).

## Why the subsidy counts towards the target

Counting the subsidy gives a smooth phase-in. Today's subsidy is about 0.82% of supply per year, well above the target, so demurrage is zero. Projection:

| Period | Target (0.30%) | Subsidy | Demurrage | Effective rate |
|---|---|---|---|---|
| 2028–2032 | ~61,500 | 82,125 | 0 | 0% |
| 2032–2036 | ~62,200 | 41,063 | ~21,100 | ~0.10% |
| 2036–2040 | ~62,600 | 20,531 | ~42,100 | ~0.20% |
| 2040–2044 | ~62,800 | 10,266 | ~52,500 | ~0.25% |
| After 2140 | ~63,000 | 0 | ~63,000 | ~0.30% |

All figures in BTC per year. Fees are paid to miners on top.

## Why 0.30%

The value is provisional. It approximates the annual cost of vaulting and insuring physical gold (roughly 0.1%–0.5%), which frames demurrage as a storage cost. That is an analogy, not a security argument.

The relevant quantity, following Budish (2018), is the ratio of the recurring security budget to the value that an attack could capture or destroy. A target of 0.30% of supply holds that ratio constant as Bitcoin's value changes, which a declining subsidy cannot do. However, 0.30% is roughly 37% of today's subsidy in BTC terms, so it implies a lower attack cost than today at equal prices. Before this BIP advances beyond draft, the target should be derived from an explicit attack-cost model.

## Why fees do not count towards the target

Letting fees reduce demurrage is attractive, but on-chain fees cannot be measured in a way that is both resistant to manipulation and impossible to route around.

**Fees paid to the includer and counted.** A miner can include a transaction paying a large fee to itself at no cost, because it collects the fee back, and each unit of measured fee cuts the next period's demurrage by one unit. An agent holding a share `s` of effective supply and a share `h` of hashrate gains `s − h` per unit of self-paid fee. A single transaction can carry any fee, so the only limit is capital. A custodian holding 6% of supply and running a mining pool with 2% of hashrate could erase the entire shortfall at no cost.

**Fees pooled and counted** (drafts 0.3.0 to 0.4.0). Paying all fees into a pool distributed over later blocks defeats self-dealing: a self-dealer recovers only `h` of its fee. But:

- a miner's marginal reward for including a transaction falls to zero, because it receives its pool share whichever miner includes the transaction;
- a user can pay the includer directly instead, through an output the miner sweeps in the same block, which consensus cannot distinguish from any other payment. At 10% hashrate this beats paying a fee for any transaction larger than about 60 vB;
- the incentive to route around the pool grows one-for-one with fees. Fees would therefore leave the measured channel as they grew, and holders would pay the full shortfall from the subsidy anyway, with extra consensus machinery.

**Fees paid to the includer and not counted.** There is nothing to manipulate, miners keep the full incentive to include transactions, and fees stay where they are today. The cost is that holders pay the subsidy's shortfall even when fees are high. In equilibrium the pooled design reaches the same outcome.

The comparison with EIP-1559 points the same way. Ethereum burns only a protocol-set base fee, which cannot be routed around, and keeps priority fees for block producers precisely to preserve the incentive to include transactions.

The dividend also smooths miner revenue. Fee-only security is vulnerable to reorganisation incentives when one block carries far more fees than the next (Carlsten et al., 2016), and recent modelling finds that small deviations in per-block revenue are enough to make dishonest mining attractive without block rewards (Lee, 2026). Subsidy plus dividend provides a steady per-block reward of at least the target.

## Why reference heights are inherited

Valuing inputs at the height a transaction is included would invalidate every pre-signed transaction whose fee margin is smaller than the decay accrued before broadcast.

An explicit per-transaction reference height, as in drafts 0.2.0 to 0.4.0, avoids this. But it needs a new serialization, transaction version, signature hash commitment and PSBT field. Tying it to a new version conflicts with TRUC transactions (BIP 431), and it still leaves transactions signed before activation exposed.

The choice of reference height is value-neutral (see Transaction valuation), so an explicit field adds no capability. Inheriting the highest reference height among a transaction's inputs is the only rule that needs no extra data and never values an input above its nominal value: an input cannot be valued at an index higher than its own `I_created`. Validity then depends only on the transaction and the outputs it spends, never on its inclusion height.

## Why the rate is set per block

Drafts 0.3.0 to 0.5.0 recalculated the rate every 2,016 blocks, from the previous 2,016 blocks. That design dates from the drafts in which fees counted towards the target and had to be measured over a period. With fees excluded, everything the rate depends on is known when a block's parent is: the subsidy schedule and `U(h − 1)`.

A rate computed from the previous period's subsidy also lags each halving. After the 2032 halving, miners would have received 66% of the target for 2,016 blocks, and the 2036 halving would have left two periods short. The floor would have failed in the weeks when the subsidy falls.

Setting the rate per block removes the lag, a parameter, and the requirement that activation coincide with a difficulty adjustment. The rate still never depends on the contents of the block being validated. Between halvings it moves only as the UTXO set value grows by the subsidy, so holders can anticipate it as well as before.

## Why fixed point with a scale of 10^18

Every node must compute identical values, so the arithmetic is specified exactly, down to its rounding. A scale of 10^18 represents the target rate (about 5.7e-8 per block) with eleven significant digits. It keeps the index meaningful for millennia: at the full target rate the index falls to about 0.05 after 1,000 years, still about 5 × 10^16 units. Rounding down everywhere means no step can create value.

## Why the index has a floor

Each step of the index rounds down, which removes up to one unit more than the rate asks for. While the index is large this is negligible, but the excess grows as the index falls. At `INDEX_MIN` it adds at most 1.75% to the full target rate. Below about 1.75 × 10^7 units the index would lose a whole unit per block whatever the rate, and would reach zero some 17 million blocks later. An index of zero has no meaning: an output created at it could not be valued.

Stopping demurrage at `INDEX_MIN` keeps every formula defined at every height. At the full target rate the index reaches `INDEX_MIN` about 6,900 years after activation. A successor rule, such as re-basing the index, can be adopted long before then. This BIP only ensures that the rules as written never fail.

## Why the UTXO set value uses a normalized total

The dividend needs the effective value of the whole UTXO set every block. Summing each output's rounded effective value would mean revaluing every output every block. The normalized total `N` changes only when outputs are created or spent, so it can be maintained as blocks are connected and disconnected, at no extra cost per block. Its precision (10^-18 of a satoshi per output) makes its rounding negligible.

## Why the timestamp rules

The dividend is paid per block. The timewarp attack lets a majority of hashrate report timestamps that lower the difficulty arbitrarily, and therefore raise the block rate arbitrarily (BIP 54). Today that brings forward a subsidy whose total is fixed. With a per-block dividend it would multiply the carrying cost of every holder for as long as it lasted, and it would pay a hashrate majority to mount the attack. BIP 54's two timestamp rules remove that ability, up to a small residual increase in the block rate, and this BIP depends on them.

Honest variation remains. When hashrate grows between difficulty adjustments, blocks arrive faster than one per ten minutes, so a calendar year can hold a few percent more than 52,560 blocks, and the charge on holders is higher in proportion. When hashrate falls, it is lower. The subsidy has always behaved the same way.

Accruing demurrage per unit of median time past, instead of per block, would remove that variation too. It would make the index, and so every valuation, depend on block timestamps, which miners choose within limits. It remains a candidate refinement.

## Why an activation marker

While the demurrage rate is zero, this BIP's valuation and coinbase rules give the same results as today's. Without a marker, nodes that never upgraded would follow the chain for years after activation, and would leave it only at the first block whose coinbase claimed a dividend, around the 2032 halving. Activation would then show nothing about how much of the network had upgraded, and the split would come at the moment the first value moved.

A block that every node without this BIP rejects makes activation the event it claims to be. The support that Deployment requires is tested at `ACTIVATION_HEIGHT`, years before any holder is charged. The highest bit of the header version is used because it can be checked from the header alone, and because it is not among the bits that mining hardware rolls.

## Why blocks commit to the demurrage state

An output's effective value depends on two things that its transaction does not contain. One is its reference height, which follows from the transaction's whole ancestry. The other is the index at that height and at the present one, which follows from the whole chain since activation. A full node has both. A client that verifies headers and Merkle proofs has neither, and without a commitment it would have to trust whoever serves it for the value of every payment it receives.

With the commitment, the value of an output can be proved to such a client. The transaction's leaf and its branch to `ref_height_root` give the reference height. The `state` of two blocks gives the index at that height and at the tip. Each is tied to a block header through the block's coinbase.

Committing to `N(h − 1)` lets a node that starts from a UTXO set snapshot check the snapshot's normalized total against the chain. It also makes any disagreement between implementations on the demurrage state visible in the first block where it arises.

## Why an optional signature hash flag

A signer needs to know what its transaction pays in fees. BIP 143 and BIP 341 made that possible offline by committing signatures to the amounts of the outputs spent. Under this BIP those amounts are no longer what consensus adds up: each input is valued at the index of the transaction's reference height, which an offline signer cannot derive. A compromised host could claim that one input is younger than it is. The signer would then believe that the other inputs are discounted, and would sign a transaction whose real fee is higher by that discount: up to 0.3% of their value for each year of the difference.

`SIGHASH_DEMURRAGE` restores the guarantee in the way BIP 143 created it. The signature commits to the values, so a false claim yields an invalid signature, not a hidden fee. The committed reference height tells the signer the index at which every amount of the transaction is expressed.

The flag is confined to taproot because taproot rejects undefined `hash_type` values, so defining new ones cannot change the validity of any existing signature. Legacy and BIP 143 signature hashes accept any `hash_type`, and redefining a bit there could invalidate signatures that exist today. A signer that spends such inputs, or declines the flag, can still bound its exposure. An input's value never exceeds its nominal amount, so the nominal amounts less the outputs are an upper bound on the fee, and are exact whenever all inputs share a reference height.

The flag also separates the two chains for those who want that. Making the separation mandatory would mean changing every signature hash, which would invalidate every pre-signed transaction and defeat the purpose of inherited reference heights (see Chain split and replay).

## Relationship to tail emission

At equal rates, demurrage and tail emission are economically equivalent. Tail emission keeps balances fixed and grows supply; demurrage keeps effective supply fixed and shrinks balances. In both cases a holder's share of the network falls at the same rate. Over ten years at 0.30%, the share falls by about 3% under either design.

This BIP does not claim that holding effective supply at 21,000,000 BTC is a substantive economic difference. It is a choice of unit of account. The substantive difference from a fixed tail emission is the schedule: this proposal is equivalent to a tail emission that phases in as the subsidy declines, so that subsidy plus emission stay at the target, and whose rate is bounded above by the target.

That choice has a cost. A tail emission with the same schedule, `block_subsidy(h) = max(halving schedule, target(h))`, would change one rule and leave amounts, wallets and Layer 2 protocols as they are. This BIP instead needs reference heights, effective values, a block commitment, and changes to every wallet and indexer. What it offers in return is that the supply figure stays at 21,000,000 BTC, and that a wallet shows a holder's share of it directly. Whether that is worth the complexity is the main open question of this proposal.

## Treatment of lost coins

Coins in abandoned outputs accrue demurrage whenever the rate is non-zero and are recycled to miners over time, without any need to prove abandonment.

## Alternatives considered

- **Fixed-rate demurrage.** Draft 0.1.0 levied a fixed 0.30% regardless of the subsidy. It charges holders while the subsidy alone exceeds the target.
- **A fee pool, with pooled fees counted towards the target.** Drafts 0.3.0 to 0.4.0. Rejected for the reasons above.
- **The median per-block fee counted towards the target.** Fees would stay with the includer, and each block's target would be reduced by the median fee per block of the previous 2,016 blocks. A miner with hashrate share `h` below 50% can only move the median to the honest `0.5 / (1 − h)` or `(0.5 − h) / (1 − h)` quantile, whatever fees it pays itself. This would let fees reduce demurrage without a pool. Its residual weakness is that a majority of hashrate could take fees out of band to raise demurrage. It remains a candidate refinement.
- **An explicit reference height.** Drafts 0.2.0 to 0.4.0. Rejected for the reasons above.
- **A rate recalculated every 2,016 blocks.** Drafts 0.3.0 to 0.5.0. Rejected for the reasons above.
- **Demurrage accrued per unit of time.** See Why the timestamp rules. It remains a candidate refinement.
- **A commitment to input values in the taproot annex.** The annex has no agreed format and is not relayed today. A `hash_type` value needs one byte and no new structure.
- **Mandatory replay protection.** It would change every signature hash and invalidate every pre-signed transaction.
- **Spend-time demurrage.** Charging accrued decay when an output is spent can be deployed as a soft fork. Lost coins never pay, and revenue arrives in large irregular amounts when long-idle coins move, unless it is smoothed through a pool of future mining revenue.
- **Tail emission.** Economically equivalent at equal rates, but permanent and unconditional.
- **Fee floors and base fees.** These stabilise fee revenue but do not create demand for block space, and cannot fund security if demand is low.

# Backward Compatibility

This is a **hard fork**. It changes the valuation of UTXOs and the coinbase validity rules, and the block at `ACTIVATION_HEIGHT` is invalid under today's rules by construction. Nodes that do not upgrade stop at that block. Deployment therefore requires overwhelming economic consensus; absent that, a persistent chain split is the expected outcome.

- **Existing transactions are unchanged.** Their format, serialization, signature hashes and versions do not change. Transaction relay policy, including TRUC (BIP 431), needs no change. Every transaction that is valid before activation remains valid after it, including pre-signed transactions, because inputs created before activation are valued at index 1.0. The one addition, `SIGHASH_DEMURRAGE`, is optional.
- **PSBT** (BIP 174, BIP 370) gains two optional per-input fields, whose key types are to be assigned: the reference height of the output spent (4 bytes, committed form), and the input's value at the transaction's reference height (8 bytes). A signer needs them to use `SIGHASH_DEMURRAGE` and to display a fee. Without them, a PSBT no longer determines its own fee.
- **Offline signers** should sign with `SIGHASH_DEMURRAGE` whenever the inputs they sign are taproot inputs. Otherwise they should display nominal amounts as upper bounds (see Why an optional signature hash flag).
- **Light clients** cannot derive a reference height or an index from a transaction and its block header. They verify both against the demurrage commitment.
- **Wallets, exchanges, indexers and explorers** must compute and report effective rather than nominal balances. UTXO set statistics computed from nominal values can exceed 21,000,000 BTC over time.
- **Wallets must denominate outputs at their transaction's reference height.** To deliver an effective amount `X`, an output's nominal amount is `X × I(ref_height) / I(now)`, where `ref_height` is the highest reference height among the transaction's inputs. Software must not add or compare nominal amounts with different reference heights without converting them.
- **Mining.** The coinbase must carry the demurrage commitment, which block templates can provide as they provide the witness commitment. Each fee is claimed as `fee_effective`, and the coinbase may also claim the dividend. The block at `ACTIVATION_HEIGHT` needs the version bit, and block timestamps must follow the two rules of Block timestamps.
- **Mempools should compare fees at a common index.** A transaction's fee is expressed at its reference height, so the fees of two transactions are not directly comparable. `fee(tx) × INDEX_ONE / I(tx.ref_height)`, the fee at index 1.0, is comparable: the ratio between the `fee_effective` of two transactions is the same in every block, so one conversion when a transaction enters the mempool is enough. Thresholds in satoshis, such as the minimum relay fee, apply to `fee_effective` in the next block.
- **Fee estimation** is unaffected for users. A transaction's fee is expressed at its reference height, which differs from its value in the next block by at most 0.3% per year since that height.
- **Lightning Network implementations** require only the balance reporting changes set out in the next section.

# Layer 2 and Lightning Network Considerations

## The problem

A Lightning channel is a 2-of-2 funding output that may remain unspent on-chain for months or years, while the channel balance is represented off-chain by pre-signed commitment transactions with fixed output amounts. If inputs were valued at the height a transaction is mined, decay on the funding output would erode the fee margin of the latest commitment transaction until it became invalid, and a party unable to broadcast a valid commitment could lose funds. The same would apply to second-stage HTLC transactions and to penalty transactions held by watchtowers.

## Commitment transactions

A commitment transaction spends only the funding output. Its reference height is the funding output's, and its single input is valued at its nominal value. Its amounts (`to_local`, `to_remote`, HTLC outputs, anchor outputs, and fee) therefore sum to at most the funding output's nominal value, exactly as today.

A commitment remains valid however long after signing it is broadcast. Its outputs inherit the funding output's reference height, so the decay accrued since then falls on each output in proportion to its value.

As a result, **decay is shared pro rata between channel parties in every state**, whether the channel closes cooperatively or by force, and whether it closes immediately or after a long idle period. No change to commitment construction and no new output type is required.

## Second-stage and penalty transactions

HTLC-success, HTLC-timeout and penalty transactions spend outputs of a commitment, so they inherit its reference height and are valued at their nominal amounts. Watchtowers can continue to hold pre-signed penalty data without refreshing it.

A party that adds a younger input to a pre-signed transaction, for example to pay fees for an HTLC transaction signed with `SIGHASH_SINGLE | SIGHASH_ANYONECANPAY`, raises the transaction's reference height. The pre-signed input is then valued slightly below its nominal value, and the added input pays the difference: at most 0.3% per year of the pre-signed amount, accrued since the funding output's reference height. Fee-bumping children spending anchors are separate transactions and are unaffected.

## Magnitude of decay on Lightning timescales

Maximum decay over typical Lightning intervals, at the full target rate, on a 0.1 BTC (10,000,000 sat) channel. Actual decay is lower whenever the subsidy covers part of the target, and zero while it covers all of it.

| Interval | Blocks | Maximum decay | On 0.1 BTC |
|---|---|---|---|
| One day | 144 | 8.2 ppm | 82 sat |
| Two-week `to_self_delay` / max CLTV | 2,016 | 115 ppm | 1,150 sat |
| One month | 4,380 | 250 ppm | 2,500 sat |
| Six months | 26,280 | 0.15% | 15,000 sat |
| One year | 52,560 | 0.30% | 30,000 sat |

## HTLCs and multi-hop payments

Payment amounts in invoices (e.g. BOLT 11 and BOLT 12) remain denominated in effective millisatoshis at the time of settlement. While payments settle off-chain, each hop's amounts are agreed in the same updated state and no discrepancy arises.

If one hop resolves an HTLC on-chain while an adjacent hop resolves off-chain, the forwarding node may receive up to the decay accrued over the on-chain resolution window, bounded by `TARGET_RATE_PER_BLOCK × cltv_expiry_delta` of the HTLC amount (under 115 ppm for deltas up to 2,016 blocks). Node operators can cover this through fee policy. No protocol change is required.

## Parameters denominated in satoshis

`dust_limit_satoshis`, `channel_reserve_satoshis`, `htlc_minimum_msat`, and similar parameters are nominal amounts at the funding output's reference height, like the commitment's own amounts. Very small outputs, including anchor outputs, decay slowly below the dust threshold over long periods (a 330 sat anchor loses at most about 1 sat per year). Such outputs become uneconomic to spend and their value eventually returns to miners through demurrage.

## Balance reporting

Wallets should report a channel balance as `state_balance × I(now) / I(funding.ref_height)`. A splice, or any transaction that spends the funding output together with a younger input, re-bases the channel to a later reference height.

## Liquidity economics

Demurrage applies identically to all on-chain value, so capital committed to a Lightning channel bears the same carrying cost as coins in cold storage. The mechanism neither penalises nor subsidises liquidity provision relative to holding. Layer 2 offers no way to avoid demurrage, because every off-chain balance is backed by a decaying funding output.

## Compatibility with proposed Lightning upgrades

Splicing and channel factories compose naturally: each new funding or allocation transaction takes the highest reference height among its inputs. Floating-transaction designs such as LN-Symmetry (which depends on `SIGHASH_ANYPREVOUT`) remain compatible, since each update transaction inherits the reference height of the output it spends. TRUC transactions (BIP 431), including zero-fee commitments with ephemeral anchors, work unchanged. `SIGHASH_DEMURRAGE` is optional, and no Lightning transaction needs it.

## Pegged and custodial systems

Federated sidechains and custodial wrapped-bitcoin products hold their backing in on-chain outputs that decay. To remain fully backed, such systems must pass demurrage through to their users, for example by applying the same index to sidechain balances or by rebasing wrapped-token supply. A system that does not do so becomes progressively under-collateralised. This is an integration requirement for those systems, not a change to Bitcoin consensus.

# Deployment

Given the hard-fork nature and the depth of the change, this BIP proposes no activation parameters at draft stage. Any activation would require:

1. Rough consensus on the bitcoin-dev mailing list and among node operators.
2. A long signalling and grace period (suggested: no less than 2 years) to allow the ecosystem to upgrade.
3. A flag-day activation height set only after demonstrated economic supermajority support.

Activation is a flag day in fact as well as in name. The block at `ACTIVATION_HEIGHT` carries the version bit described in Activation block, so nodes that have not upgraded stop there, and the two rule sets cannot share a chain afterwards.

Because the demurrage rate is zero while the subsidy exceeds the target, activation before the 2032 halving would impose no cost on holders until then. This allows the full software stack to be deployed and tested in production before demurrage first applies.

Nodes need the total value of the UTXO set at `ACTIVATION_HEIGHT − 1`. They should compute it ahead of that height and keep it current (see UTXO set value), so that no node pauses at activation. A node upgraded after that height must re-validate the blocks from it. It must not reuse what it derived from those blocks before upgrading, such as its record of the outputs each block spent, which lacks their reference heights. UTXO set snapshots (such as assumeutxo) whose base is at or above `ACTIVATION_HEIGHT` must carry the demurrage index of every height since activation, the rate and the normalized UTXO total. All of them can be checked against the demurrage commitments.

## Chain split and replay

If both rule sets keep miners after `ACTIVATION_HEIGHT`, there are two chains that share every output created before it. A transaction that spends only such outputs, and is signed without `SIGHASH_DEMURRAGE`, is valid on both and can be replayed from one to the other. That is the price of keeping pre-signed transactions valid: no rule can reject replays without rejecting them too.

Protection is therefore opt-in:

- a transaction with at least one signature that uses `SIGHASH_DEMURRAGE` is valid only on the chain that applies this BIP;
- a transaction that spends an output descended from a coinbase mined at or after `ACTIVATION_HEIGHT` is valid only on the chain of that coinbase.

Spending an output on one chain with such a transaction separates it. The output is then spent on that chain only, so a later transaction that spends it on the other chain cannot be replayed either. Wallets should offer this before a holder transacts on either chain.

# Security Considerations

**Fee manipulation.** Fees, whether paid on-chain or out of band, do not affect the rate, so there is nothing to gain by paying fees to oneself or by moving them off-chain. Out-of-band fee payments remain possible as today, with the same centralisation concerns, and this proposal adds no incentive for them.

**UTXO set value.** The rate depends on `U(h − 1)`. Destroying coins (for example through `OP_RETURN` outputs or coinbases that claim less than their limit) lowers it and therefore the rate, but costs the destroyer the coins destroyed.

**Inclusion incentive.** Unchanged from today: the miner that includes a transaction receives its fee.

**Rate variability.** Holders face a carrying cost between zero and the target rate per block. It steps at each halving, moves only slightly between halvings as the UTXO set value grows, and can be anticipated years in advance.

**Block production rate.** The charge accrues per block. The timestamp rules prevent a majority of hashrate from accelerating blocks through the timewarp attack. A calendar year can still hold a few percent more or fewer than 52,560 blocks as hashrate changes, and the charge on holders varies with it.

**Target calibration.** The target is provisional and not yet derived from an attack-cost model. A target set too low leaves the security budget inadequate; one set too high imposes an unnecessary cost on holders.

**Capital flight.** A store-of-value asset with a carrying cost competes against substitutes without one, including any non-demurrage fork of Bitcoin. This remains the principal risk to the proposal. The target-based design reduces it relative to a fixed rate, because no cost applies while the subsidy exceeds the target, but does not remove it.

**Perceived confiscation.** Holders observe their effective balances decline whenever the rate is non-zero. This may provoke stronger resistance than dilution, which is not visible on a holder's own balance.

**Implementation determinism.** The demurrage rate, the index, reference heights and the UTXO set value must be computed identically across all implementations, using fixed-point integer arithmetic. The demurrage commitment makes a divergence visible in the first block where it arises.

**Pre-signed transaction validity.** A transaction's validity does not depend on its inclusion height. Only a reorganisation at least 100 blocks deep could change the index at a transaction's reference height.

**Unit of nominal amounts.** Nominal amounts are expressed at different indexes. Software that adds or compares them without converting them to effective values will misreport balances.

**Offline signers.** A signer that does not use `SIGHASH_DEMURRAGE` cannot verify the values of the inputs it spends, and a compromised host can make it pay a higher fee than the one it displays. The nominal amounts bound the loss. Signers should use the flag wherever they can.

**Light clients.** A client that does not check demurrage commitments must trust its server for the effective value of every output. A proof against a commitment is as strong as the proof of work on the header that carries it, like any other light client proof.

**Chain split and replay.** Replay protection is opt-in, by design (see Chain split and replay).

**Index floor.** Demurrage stops when the index reaches `INDEX_MIN`, about 6,900 years after activation at the full target rate. From then on the security budget depends on fees alone, unless a successor rule is adopted.

**No new incentive to force-close.** Because decay is attributed pro rata in every channel state, a party gains nothing by forcing, delaying or refusing a channel update.

**Privacy.** Reference heights are derived from public chain data, and no new field reveals when a transaction was signed.

# Reference Implementation

A reference implementation against Bitcoin Core is available at [cpopov/bitcoin#1](https://github.com/cpopov/bitcoin/pull/1). It is not scheduled on any network; on regtest it activates with `-testactivationheight=demurrage@<height>`. It implements this draft:

- the fixed-point demurrage index, per-block rate, index floor, UTXO set value and dividend, with per-block state stored alongside the block index so that it survives restarts and reorganisations;
- inherited reference heights, stored with each UTXO and derived through unconfirmed ancestors in the mempool;
- transaction valuation and the revised coinbase limit;
- the timestamp rules, the activation block and the demurrage commitment, in validation, in block templates and in `getblocktemplate`;
- `SIGHASH_DEMURRAGE` in script validation, for blocks and for the mempool, and signing with it in the wallet and the node's PSBT signer;
- opt-in replay protection: with `-walletdemurragesighash`, the wallet signs the transactions it sends with `SIGHASH_ALL | SIGHASH_DEMURRAGE`, which separates the coins they spend when one of them is a taproot output. Its coin selection prefers an input set that has either a taproot output or a separated output: one descended from a coinbase mined at or after `ACTIVATION_HEIGHT` (whose reference height is at or above it), or from a transaction with a `SIGHASH_DEMURRAGE` signature;
- the two PSBT fields, recorded by the wallet and the node and used by signers. Until their key types are assigned, it encodes them as proprietary keys (`0xFC`) with identifier `bip462` and no key data: subtype `0x00` for the reference height and `0x01` for the value;
- the UTXO set value computed ahead of `ACTIVATION_HEIGHT − 1`, at a height each node picks at random, and kept current from then on;
- effective-value computation in validation, the mempool, mining, the wallet and RPC.

It does not implement:

- replay protection for a wallet with neither kind of output to spend, for example by first obtaining an output descended from a coinbase mined at or after `ACTIVATION_HEIGHT`;
- proofs of a reference height against the demurrage commitment, for light clients.

It departs from one recommendation. Its mempool does not keep the fee at index 1.0. It keeps `fee_effective` in the next block, converted once when the transaction enters. The two rank transactions alike, except for the demurrage that accrues while they wait, and the second is in the unit of the thresholds.

Its `doc/bip462.md` maps each part of this BIP to the code and lists its limitations. Its `doc/bip462-design-review.md` records the analysis behind the changes in draft 0.5.0.

Prior art exists: Freicoin (2012, by Jorge Timón and Mark Friedenbach) implemented demurrage on a Bitcoin-derived codebase, with proceeds recirculated as a perpetual mining reward.

# Test Vectors

Test vectors are provided in [`bip-0462/test-vectors.json`](bip-0462/test-vectors.json). They were computed with an implementation of this BIP's arithmetic that is independent of the reference implementation's consensus code, and the reference implementation passes all of them.

1. `rate`: demurrage rates for a UTXO set value, a block subsidy and the index of the previous block, including at and around `INDEX_MIN`.
2. `index`: demurrage index values over sequences of rates.
3. `index_floor`: the blocks in which the index reaches `INDEX_MIN` and stops falling.
4. `effective_value`: effective values of outputs created at different indexes.
5. `utxo_value`: normalized values of outputs and the UTXO set value they give.
6. `dividend`: demurrage dividends.
7. `chain`: a chain of blocks from activation, with each block's rate, index, dividend, fees, coinbase limit and UTXO set value.
8. `inputs`: transactions spending outputs with different reference heights, with their inherited reference height, validity and fee.
9. `commitment`: demurrage commitments, with the committed form of each reference height, `ref_height_root` and the coinbase output script.
10. `sighash`: the signature message and hash for the `hash_type` values `0x41`, `0x42` and `0x43`, on the key path and the script path, with the value of each input and the committed reference height.

All fixed-point values are integers scaled by `INDEX_ONE`. Values that do not fit in 64 bits are given as decimal strings. The file is generated by `contrib/bip462/gen_test_vectors.py` in the reference implementation.
