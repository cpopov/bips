# Abstract

This BIP proposes a **security budget floor** for Bitcoin. Each difficulty period, the protocol compares what miners were paid in the previous period (block subsidy plus transaction fees) with a target of **0.30% of effective supply per year**. Any shortfall is made up by a **demurrage**: a small carrying cost levied on every unspent transaction output (UTXO) and paid to miners. When subsidy and fees meet the target, the demurrage rate is zero.

Because today's subsidy alone exceeds the target, demurrage would not apply until the early 2030s, and would apply only to the extent that fees have not grown to replace the subsidy. Transaction fees are paid into a pool distributed over subsequent blocks, so that miners cannot cheaply inflate measured fees to suppress demurrage. Effective supply follows the existing issuance schedule and never exceeds 21,000,000 BTC.

# Motivation

Bitcoin's security model relies on two miner revenue streams: the block subsidy and transaction fees. The subsidy halves approximately every four years and trends to zero around 2140, so long-term security depends on fees replacing it.

There is credible doubt that they will. In 2026, fees fell to between 0.5% and 0.7% of miner revenue while daily transaction counts reached record levels. Fees are priced by competition for block space, which is not currently scarce. Neither the volume of activity nor the value being secured enters that price. Bitcoin is also predominantly held rather than spent, and holding pays nothing towards security.

Budish (2018) shows that for majority attacks to remain unprofitable, the recurring payments to miners (a flow) must remain large relative to the value an attack could capture or destroy (a stock). A subsidy that halves towards zero moves in the opposite direction as Bitcoin's value grows.

The widely discussed remedies each break a core property: tail issuance abandons the 21,000,000 BTC schedule, and proof-of-stake abandons proof-of-work. A fixed-rate demurrage preserves both but charges holders permanently, even if fees later prove sufficient.

This proposal sets a floor instead. It charges holders only for the part of the security budget that subsidy and fees fail to cover, and only for as long as they fail to cover it.

# Specification

## Overview

1. A global **demurrage index** tracks cumulative decay since activation. Each UTXO records the index at creation, and its effective (spendable) value is its nominal value scaled by the fall in the index since.
2. The per-block demurrage rate is recalculated every **rate period** of 2,016 blocks, from the shortfall between a target budget and the subsidy and fees paid in the previous period. The rate is between zero and the target rate.
3. Each block's miner may claim a **demurrage dividend** equal to the decay accrued across the UTXO set during that block.
4. Transaction fees enter a **fee pool** and are paid out to miners over subsequent blocks rather than to the miner who includes the transaction.
5. A per-transaction **reference height** keeps pre-signed transactions valid.

## Parameters

```
TARGET_RATE_ANNUAL      = 0.0030             (0.30% of effective supply per year)
BLOCKS_PER_YEAR         = 52,560             (≈ 144 blocks/day)
TARGET_RATE_PER_BLOCK   = TARGET_RATE_ANNUAL / BLOCKS_PER_YEAR
                        = 3 / 52,560,000     (≈ 5.708e-8)
RATE_PERIOD             = 2,016 blocks       (aligned with difficulty adjustment)
FEE_POOL_DIVISOR        = 1,000              (fee pool half-life ≈ 693 blocks)
INDEX_ONE               = 10^18              (fixed-point scale of the index and the rate)
ACTIVATION_HEIGHT       = [to be set; see Deployment]
```

All parameters are consensus constants. None is adjustable by miners, nodes, or any governance process. `ACTIVATION_HEIGHT` must be a multiple of 2,016, so that rate periods coincide with difficulty adjustment periods.

## Fixed-point arithmetic

All arithmetic is performed on integers. Floating-point arithmetic must not be used.

- Amounts are integers in satoshis.
- The demurrage index `I(h)` and the per-block rate `r_k` are integers scaled by `INDEX_ONE`: an index of `INDEX_ONE` means 1.0, and a rate of 57,077,625,570 means about 5.708e-8 per block.
- Every division rounds down (`floor`). Intermediate products must be computed exactly; they need up to 256 bits.

The test vectors give the expected result of every formula in this section and the next ones.

## Demurrage rate

Rate period `k` (for `k = 0, 1, 2, …`) begins at height `H_k = ACTIVATION_HEIGHT + k × RATE_PERIOD` and covers `RATE_PERIOD` blocks. Its rate is:

```
U_k          = U(H_k − 1)                                  (see UTXO set value)
target_k     = floor(U_k × RATE_PERIOD × 3 / 52,560,000)   (TARGET_RATE_PER_BLOCK × U_k × RATE_PERIOD)
covered_k    = subsidy_{k−1} + fees_{k−1}
shortfall_k  = max(0, target_k − covered_k)
r_k          = floor(shortfall_k × INDEX_ONE / (RATE_PERIOD × U_k))     (r_k = 0 if U_k = 0)
```

where:

- `subsidy_{k−1}` is the sum of the block subsidy schedule over the blocks of period `k−1`: the amount each block was entitled to under the halving schedule, whatever its coinbase actually claimed.
- `fees_{k−1}` is the total of `fee_effective` (defined below) paid into the fee pool during period `k−1`.
- For the first period (`k = 0`), period `k−1` is the `RATE_PERIOD` blocks preceding activation, from `ACTIVATION_HEIGHT − RATE_PERIOD` to `ACTIVATION_HEIGHT − 1`. There is no pool before activation, so its fees are the plain fees of those blocks: the input values less the output values of every non-coinbase transaction. Nodes must therefore track subsidy and fees from `ACTIVATION_HEIGHT − RATE_PERIOD`.

By construction `0 ≤ r_k ≤ floor(INDEX_ONE × 3 / 52,560,000) = 57,077,625,570`, the target rate. The rate for each period is fully determined by data already on-chain when the period begins.

## Demurrage index

Maintain a cumulative index `I(h)` with `I(h) = INDEX_ONE` (1.0) for every `h < ACTIVATION_HEIGHT` and, for each block `h` in rate period `k`:

```
I(h) = floor(I(h−1) × (INDEX_ONE − r_k) / INDEX_ONE)
```

The index is non-increasing and deterministic. Its value at any past height is known to every node.

## UTXO valuation

Each UTXO has an `I_created`, the index applicable to the transaction that created it:

- for an output created before activation, `I_created = I(ACTIVATION_HEIGHT − 1) = INDEX_ONE`;
- for an output created by a transaction with a reference height, `I_created = I(ref_height)` (see Transaction reference height);
- for an output created by a legacy-version transaction or a coinbase, `I_created = I(h)`, where `h` is the height of the block that includes it.

Implementations store each output's reference height (for outputs created after activation) and look up `I_created` from it. The effective value of a UTXO with nominal value `v` at height `h` is:

```
effective_value(h) = floor(v × I(h) / I_created)
```

Rounding down discards less than one satoshi each time an output is valued. These remainders are not credited to anyone: they cannot be paid into a pool that holds whole satoshis. See Supply accounting.

## UTXO set value

`U(h)`, the effective value of the UTXO set after block `h`, is defined through the UTXO set's normalized total `N(h)`, so that it can be maintained incrementally:

```
n(o)  = floor(v × INDEX_ONE² / I_created)        (normalized value of an unspent output o)
N(h)  = sum of n(o) over the UTXO set after block h
U(h)  = floor(N(h) × I(h) / INDEX_ONE²)
```

`N` changes only when outputs are created or spent: each block adds `n(o)` for every output it adds to the UTXO set, and subtracts `n(o)` for every output it spends. Outputs that are never added to the UTXO set, such as provably unspendable `OP_RETURN` outputs, do not count.

`U(h)` is not the sum of each output's rounded effective value. Such a sum would have to be recomputed over the whole UTXO set every block, because every output's rounding changes as the index falls.

At `ACTIVATION_HEIGHT − 1`, every output has `I_created = INDEX_ONE`, so `N = INDEX_ONE × (total value of the UTXO set)`. Implementations compute this once, by scanning the UTXO set, when their chain reaches `ACTIVATION_HEIGHT − 1`.

## Transaction reference height

Valuing inputs at the height a transaction is included would invalidate every pre-signed transaction whose fee margin is smaller than the decay accrued before broadcast. This BIP therefore introduces a per-transaction **reference height** in a new transaction version.

Transactions of version 4 or higher carry a field `ref_height`, a 32-bit unsigned integer.

### Serialization

`ref_height` uses the extended transaction serialization of BIP 144, with bit 1 (`0x02`) of the flag byte marking its presence:

```
nVersion | marker 0x00 | flag | txins | txouts | [witnesses, if flag & 0x01] | nLockTime | [ref_height, if flag & 0x02]
```

`ref_height` is encoded as 4 bytes, little-endian, after `nLockTime`. A transaction with both witnesses and a reference height has flag `0x03`.

`ref_height` is non-witness data. The marker, the flag and `ref_height` are part of the serialization used for the txid, even when the transaction has no witnesses, so the txid commits to the reference height. For a transaction with a reference height but no witnesses, the wtxid equals the txid. For weight, all three count as non-witness bytes.

The presence of the field is signalled by the flag, not by the version, because a parser must know the layout before it can validate anything. `nVersion` was unconstrained before BIP 68, so historical transactions may carry any version, including 4. Before this BIP every flag value other than `0x01` was rejected as unknown, so no historical transaction can be misparsed.

### Validation rules

The field's presence is checked first:

- Before `ACTIVATION_HEIGHT`, a transaction carrying `ref_height` is invalid.
- From `ACTIVATION_HEIGHT`, a non-coinbase transaction carries `ref_height` if and only if its version is 4 or higher. A coinbase must not carry it.

A transaction with a reference height must then satisfy:

1. `ref_height` must be greater than or equal to the reference height of every output it spends (for outputs created before activation, `ACTIVATION_HEIGHT`; otherwise the `ref_height` of the transaction that created it, or, for outputs of legacy-version transactions and coinbases, the height of the block that included them).
2. `ref_height` must be less than or equal to the height of the block that includes the transaction. A transaction whose `ref_height` is in the future is not yet valid.
3. All inputs are valued at `I(ref_height)`: `input_value = floor(v × I(ref_height) / I_created)`.
4. Every output created by the transaction is assigned `I_created = I(ref_height)`.
5. The transaction is valid if the sum of its output values does not exceed the sum of its input values, both evaluated at `ref_height`. Its fee is `fee(tx) = sum(input_value) − sum(output values)`.

Rule 1 also gives every transaction `ref_height ≥ ACTIVATION_HEIGHT`, since it ultimately spends outputs created before activation. Note that an output created before activation has reference height `ACTIVATION_HEIGHT` for rule 1, but `I_created = I(ACTIVATION_HEIGHT − 1)` for valuation.

The reference height is value-neutral. Outputs created with an earlier `ref_height` begin life already carrying the decay accrued since that height, so the choice of reference height neither avoids nor brings forward any demurrage. Decay between `ref_height` and inclusion falls on every output in proportion to its value.

Legacy-version transactions are treated as having `ref_height` equal to their inclusion height.

### Signature hashes

Signatures commit to the reference height. Otherwise anyone could change it, which would change the value of the transaction's inputs, its fee and its txid. When a transaction carries `ref_height`, its 4-byte little-endian encoding is appended immediately after `nLockTime` in each signature message:

- legacy (pre-segwit) signatures: in the serialized transaction, after `nLockTime` and before the sighash type;
- BIP 143 (witness v0): after `nLockTime` and before the sighash type;
- BIP 341 (taproot): in `SigMsg`, after `nLockTime`, so that the maximum length of `SigMsg` becomes 210 bytes.

The signature messages of transactions without a reference height are unchanged.

## Fee pool

Transaction fees are not paid to the miner of the block that includes them. They are paid into a consensus-tracked **fee pool** and distributed over subsequent blocks:

```
fee_effective(tx, h) = floor(fee(tx) × I(h) / I(tx.ref_height))
total_fees(h)        = sum of fee_effective(tx, h) over all transactions in block h
pool_payout(h)       = floor(pool(h−1) / FEE_POOL_DIVISOR)
pool(h)              = pool(h−1) − pool_payout(h) + total_fees(h)
```

For a legacy-version transaction, `ref_height` is the inclusion height, so `fee_effective = fee`.

The pool starts at zero at activation. Its balance does not decay. Fees paid in a block are distributed geometrically over the following blocks, with a half-life of approximately 693 blocks (about 4.8 days).

## Coinbase

For each block at height `h` in rate period `k`, the miner may claim:

```
demurrage_dividend(h) = floor(r_k × U(h−1) / INDEX_ONE)
```

where `U(h−1)` is the effective value of the UTXO set after block `h−1` (see UTXO set value).

Consensus rule: a block is invalid if its coinbase output value exceeds:

```
block_subsidy(h) + pool_payout(h) + demurrage_dividend(h)
```

The limit depends on the chain state (`U(h−1)` and the pool), so it is checked when the block is connected to the chain, not in context-free block checks. Any part of the limit that the coinbase does not claim is destroyed; it is not returned to the fee pool.

## Supply accounting

The demurrage dividend is minted at face value in the coinbase while existing outputs keep their nominal values. The sum of nominal UTXO values therefore grows over time. Nominal values have no economic meaning after activation; wallets, exchanges and indexers must report effective values.

**Effective supply**, the effective value of the UTXO set plus the fee pool, is conserved by demurrage and by fees: what holders lose to decay, miners receive as dividend, and fees move from outputs to the pool to miners. Effective supply changes only through the block subsidy, so it follows the existing issuance schedule and never exceeds 21,000,000 BTC.

Conservation holds up to rounding down. Each block can lose up to about one satoshi per input it spends and per transaction it includes, plus a few satoshis from the dividend and the UTXO set value, and it never gains. A coinbase that claims less than its limit also reduces effective supply.

No individual output's nominal value can exceed 21,000,000 BTC, because it equals its effective value at its own reference height. The existing range checks on output values therefore remain valid. Only the sum of nominal values can exceed that amount.

## Interaction with the existing subsidy

The halving schedule is unchanged. The subsidy counts towards the target, so while subsidy alone exceeds the target the demurrage rate is zero. As halvings reduce the subsidy, demurrage phases in automatically to the extent fees do not cover the difference. No special handling is required at any halving or when the subsidy reaches zero.

# Rationale

## Why a target rather than a fixed rate

A fixed rate charges holders whether or not they need to. A target charges them only for the part of the security budget that subsidy and fees fail to cover. If fees grow enough to replace the subsidy, demurrage never applies. This makes the mechanism a backstop rather than a permanent charge, and ties the cost to holders directly to whether the fee market is working.

The target is expressed as a fraction of effective supply in BTC, and subsidy and fees are measured on-chain in BTC. The rate can therefore be computed by every node without a price oracle. A target expressed in fiat terms would require a price feed that cannot be obtained trustlessly.

## Why the subsidy counts towards the target

Counting the subsidy gives a smooth phase-in. Today's subsidy is about 0.82% of supply per year, well above the target, so demurrage is zero. Illustrative projection, assuming fees stay at their 2026 level of roughly 1,000 BTC per year:

| Period | Target (0.30%) | Subsidy | Demurrage needed | Effective rate |
|---|---|---|---|---|
| 2028–2032 | ~61,500 | 82,125 | 0 | 0% |
| 2032–2036 | ~62,200 | 41,063 | ~20,000 | ~0.10% |
| 2036–2040 | ~62,600 | 20,531 | ~41,000 | ~0.20% |
| 2040–2044 | ~62,800 | 10,266 | ~51,500 | ~0.25% |
| After 2140 | ~63,000 | 0 | ~62,000 | ~0.30% |

All figures in BTC per year. Any growth in fees reduces the demurrage required one-for-one.

## Why 0.30%

The value is provisional. It approximates the annual cost of vaulting and insuring physical gold (roughly 0.1%–0.5%), which frames demurrage as a storage cost. That is an analogy, not a security argument.

The relevant quantity, following Budish (2018), is the ratio of the recurring security budget to the value that an attack could capture or destroy. A target of 0.30% of supply holds that ratio constant as Bitcoin's value changes, which a declining subsidy cannot do. However, 0.30% is roughly 37% of today's subsidy in BTC terms, so it implies a lower attack cost than today at equal prices. Before this BIP advances beyond draft, the target should be derived from an explicit attack-cost model.

## Why a fee pool

Without a fee pool, a miner can include a transaction paying a large fee to themselves at no cost, because they collect the fee back. Under a target-based rate, inflated fees reduce the next period's demurrage, which benefits holders. Any party whose share of coins exceeds its share of hashrate would profit from this, and holders as a group gain more than miners as a group lose, so the incentive to manipulate is persistent.

With a fee pool, a fee paid in block `h` is distributed to miners of subsequent blocks in proportion to the blocks they find. A party paying a fee `F` to itself recovers only about `h_share × F`, loses `h_share × F` of future dividend, and gains `s_share × F` as a holder, where `h_share` and `s_share` are its shares of hashrate and of effective supply. The net result is `(s_share − 1) × F`, which is negative for any party not holding the entire supply.

The pool also smooths miner revenue. Fee-only security is vulnerable to reorganisation incentives when one block carries far more fees than the next (Carlsten et al., 2016), and recent modelling finds that small deviations in per-block revenue are enough to make dishonest mining attractive without block rewards (Lee, 2026). A geometric payout with a half-life of several days removes most of that variance. The same reasoning underlies Ethereum's decision to burn the base fee rather than pay it to block producers (EIP-1559).

## Why the rate period matches difficulty adjustment

Recalculating every 2,016 blocks gives holders a rate that is known in advance for about two weeks, reuses an interval that implementations already track, and lags measurement by one period so that the rate never depends on the contents of the block being validated.

## Why fixed point with a scale of 10^18

Every node must compute identical values, so the arithmetic is specified exactly, down to its rounding. A scale of 10^18 represents the target rate (about 5.7e-8 per block) with eleven significant digits. It keeps the index meaningful for millennia: at the full target rate the index falls to about 0.05 after 1,000 years, still about 5 × 10^16 units. Rounding down everywhere means no step can create value.

## Why the UTXO set value uses a normalized total

The dividend needs the effective value of the whole UTXO set every block. Summing each output's rounded effective value would mean revaluing every output every block. The normalized total `N` changes only when outputs are created or spent, so it can be maintained as blocks are connected and disconnected, at no extra cost per block. Its precision (10^-18 of a satoshi per output) makes its rounding negligible.

## Why the reference height is flagged in the serialization

A rule such as "version 4 transactions have an extra field after `nLockTime`" cannot be applied to the existing chain, which may contain version 4 transactions from before BIP 68 constrained versions. The extended serialization's flag byte was introduced by BIP 144 with every value other than `0x01` reserved, so bit `0x02` is unused in every existing transaction. The version requirement is kept as a validation rule, so that the version still states the transaction's semantics.

## Relationship to tail emission

At equal rates, demurrage and tail emission are economically equivalent. Tail emission keeps balances fixed and grows supply; demurrage keeps effective supply fixed and shrinks balances. In both cases a holder's share of the network falls at the same rate. Over ten years at 0.30%, the share falls by about 3% under either design.

This BIP does not claim that holding effective supply at 21,000,000 BTC is a substantive economic difference. It is a choice of unit of account. The substantive differences from a fixed tail emission are that this proposal charges holders only when subsidy and fees fall short, and that its rate is bounded above by the target.

## Treatment of lost coins

Coins in abandoned outputs accrue demurrage whenever the rate is non-zero and are recycled to miners over time, without any need to prove abandonment.

## Alternatives considered

- **Fixed-rate demurrage.** An earlier version of this draft levied a fixed 0.30% regardless of fee revenue. It charges holders even when fees are sufficient and was replaced by the target-based rate.
- **Spend-time demurrage.** Charging accrued decay as a required fee when an output is spent could be deployed as a soft fork. Lost coins would never pay, revenue would arrive in large irregular amounts when long-idle coins move, and pre-signed transactions would again become invalid. Large irregular fees are the reorganisation risk this proposal aims to reduce.
- **Tail emission.** Economically equivalent at equal rates, but permanent and unconditional.
- **Fee floors and base fees.** These stabilise fee revenue but do not create demand for block space, and cannot fund security if demand is low.

# Backward Compatibility

This is a **hard fork**. It changes coinbase validity rules, the valuation of UTXOs, and where transaction fees are paid. Nodes that do not upgrade will reject blocks produced under the new rules. Deployment therefore requires overwhelming economic consensus; absent that, a persistent chain split is the expected outcome.

- **Wallets, exchanges, indexers and explorers** must compute and report effective rather than nominal balances. UTXO set statistics computed from nominal values can exceed 21,000,000 BTC over time.
- **Transaction parsers** must accept the `0x02` flag bit and the trailing `ref_height` field.
- **Wallets must create version 4 transactions to be relayed.** A legacy-version transaction is valued at its inclusion height, so its fee shrinks, and it can become invalid, with every block it waits. A mempool cannot hold such transactions consistently, so nodes should not relay legacy-version transactions after activation. They remain valid in blocks.
- **Mining pools** must account for fees arriving through the pool payout rather than directly. Pool payout schemes that attribute fees to the block that included them will need revision.
- **Fee estimation** is unaffected for users: fees are still paid by transactions and still compete for block space.
- **PSBT.** In PSBTv0 (BIP 174) the unsigned transaction carries `ref_height`, so it uses the extended serialization even without witnesses, and parsers must accept that there. PSBTv2 (BIP 370) needs a new global field for the reference height; the reference implementation provisionally uses key type `0x07` (`PSBT_GLOBAL_REF_HEIGHT`) and a 4-byte value.
- **Lightning Network implementations** require the changes set out in the next section.

# Layer 2 and Lightning Network Considerations

## The problem

A Lightning channel is a 2-of-2 funding output that may remain unspent on-chain for months or years, while the channel balance is represented off-chain by pre-signed commitment transactions with fixed output amounts. Without the reference height mechanism, decay on the funding output would erode the fee margin of the latest commitment transaction until it became invalid, and a party unable to broadcast a valid commitment could lose funds. The same applies to second-stage HTLC transactions and to penalty transactions held by watchtowers.

## Commitment transactions

Every commitment transaction sets `ref_height` to a recent block height at the time the parties sign it. All amounts in the commitment (`to_local`, `to_remote`, HTLC outputs, anchor outputs, and fee) are denominated in effective value at that height, so they must sum to no more than:

```
funding_effective(ref_height) = funding_value × I(ref_height) / I_funding
```

On each state update the parties may advance `ref_height` and re-base balances to the new effective funding value. A commitment broadcast long after it was signed remains valid, and the decay accrued since its `ref_height` falls on each output in proportion to its value.

As a result, **decay is shared pro rata between channel parties in every state**, whether the channel closes cooperatively or by force, and whether it closes immediately or after a long idle period. No new output type is required.

## Second-stage and penalty transactions

HTLC-success and HTLC-timeout transactions inherit the commitment's `ref_height` (or any later height up to inclusion). Penalty transactions spending outputs of a revoked commitment may use the revoked commitment's `ref_height`, which satisfies rule 1 of the reference height specification. Watchtowers can therefore continue to hold pre-signed penalty data without refreshing it.

## Magnitude of decay on Lightning timescales

Maximum decay over typical Lightning intervals, at the full target rate, on a 0.1 BTC (10,000,000 sat) channel. Actual decay is lower whenever subsidy and fees cover part of the target, and zero while they cover all of it.

| Interval | Blocks | Maximum decay | On 0.1 BTC |
|---|---|---|---|
| One day | 144 | 8.2 ppm | 82 sat |
| Two-week `to_self_delay` / max CLTV | 2,016 | 115 ppm | 1,150 sat |
| One month | 4,380 | 250 ppm | 2,500 sat |
| Six months | 26,280 | 0.15% | 15,000 sat |
| One year | 52,560 | 0.30% | 30,000 sat |

## HTLCs and multi-hop payments

Payment amounts in invoices (e.g. BOLT 11 and BOLT 12) remain denominated in effective millisatoshis at the time of settlement. While payments settle off-chain, each hop's amounts are agreed in the same updated state and no discrepancy arises.

If one hop resolves an HTLC on-chain while an adjacent hop resolves off-chain, the forwarding node may receive up to the decay accrued over the on-chain resolution window, bounded by `TARGET_RATE_PER_BLOCK × cltv_expiry_delta` of the HTLC amount (under 115 ppm for deltas up to 2,016 blocks). Node operators can cover this through fee policy. No protocol change is required.

## Parameters denominated in satoshis

`dust_limit_satoshis`, `channel_reserve_satoshis`, `htlc_minimum_msat`, and similar parameters are interpreted as effective values at the commitment's `ref_height`. Very small outputs, including anchor outputs, decay slowly below the dust threshold over long periods (a 330 sat anchor loses at most about 1 sat per year). Such outputs become uneconomic to spend and their value eventually returns to miners through demurrage.

## Balance reporting

Wallets should report a channel balance as `state_balance × I(now) / I(state.ref_height)`. Channels that update frequently re-base automatically. Idle channels may perform a no-op state update to refresh their reference height, but this is a display convenience and not required for safety.

## Liquidity economics

Demurrage applies identically to all on-chain value, so capital committed to a Lightning channel bears the same carrying cost as coins in cold storage. The mechanism neither penalises nor subsidises liquidity provision relative to holding. Layer 2 offers no way to avoid demurrage, because every off-chain balance is backed by a decaying funding output.

## Compatibility with proposed Lightning upgrades

Splicing and channel factories compose naturally, since each new funding or allocation transaction carries its own `ref_height`. Floating-transaction designs such as LN-Symmetry (which depends on `SIGHASH_ANYPREVOUT`) remain compatible, provided each update transaction sets a `ref_height` no earlier than that of the state it replaces.

**Open question: TRUC transactions.** Current commitment designs use version 3 TRUC transactions (BIP 431), for example zero-fee commitments with ephemeral anchors. Under this specification a reference height requires version 4 or higher, so a commitment transaction cannot be both TRUC and pre-signed safely. Either the TRUC policy must be extended to a version that carries a reference height, or the reference height must be decoupled from the version and signalled by the serialization flag alone.

## Pegged and custodial systems

Federated sidechains and custodial wrapped-bitcoin products hold their backing in on-chain outputs that decay. To remain fully backed, such systems must pass demurrage through to their users, for example by applying the same index to sidechain balances or by rebasing wrapped-token supply. A system that does not do so becomes progressively under-collateralised. This is an integration requirement for those systems, not a change to Bitcoin consensus.

# Deployment

Given the hard-fork nature and the depth of the change, this BIP proposes no activation parameters at draft stage. Any activation would require:

1. Rough consensus on the bitcoin-dev mailing list and among node operators.
2. A long signalling and grace period (suggested: no less than 2 years) to allow the ecosystem to upgrade.
3. A flag-day activation height set only after demonstrated economic supermajority support.

Because the demurrage rate is zero while the subsidy exceeds the target, activation before the 2032 halving would impose no cost on holders until then. This allows the full software stack, including reference heights and the fee pool, to be deployed and tested in production before demurrage first applies.

Two requirements fall on nodes before activation:

- Nodes must track the subsidy and fees of every block from `ACTIVATION_HEIGHT − RATE_PERIOD`, because the first rate depends on them. A node upgraded after that height must re-validate those blocks.
- Nodes must compute the UTXO set value at `ACTIVATION_HEIGHT − 1`, which requires one scan of the UTXO set.

UTXO set snapshots (such as assumeutxo) must carry the demurrage state if their base is at or above `ACTIVATION_HEIGHT − RATE_PERIOD`.

# Security Considerations

**Out-of-band fee payments.** Fees paid to miners off-chain, for example through transaction accelerator services, are not measured and do not reduce the demurrage rate. Under this proposal the incentive to move fees off-chain increases: the fee pool prevents a miner from keeping an on-chain fee for itself, and fees moved off-chain are replaced by demurrage paid to all miners. This cannot be prevented by on-chain rules. The mechanism should therefore be understood as guaranteeing a **security budget floor** of the target rate; the share of that floor covered by fees rather than demurrage depends on how much of the fee market remains on-chain. In the worst case, the rate converges to the target and the proposal behaves as fixed-rate demurrage.

**Fee self-dealing.** Mitigated by the fee pool, as described in the Rationale. Without the pool, the target-based rate would be manipulable at no cost by any party with more stake than hashrate.

**Inclusion incentive.** The fee pool also weakens a miner's incentive to include transactions. A miner with hashrate share `h_share` eventually receives only `h_share × F` of a fee `F` that it includes; the rest goes to other miners. Including transactions becomes a public good among miners, with a marginal reward for filling a block close to zero, and the incentive to take fees out of band (see above) grows. The effect on block space supply has not been analysed.

**Rate variability.** Holders face a carrying cost that varies between zero and the target rate from one period to the next. The rate is known two weeks in advance, is bounded, and is counter-cyclical: it is highest when on-chain demand is weakest.

**Target calibration.** The target is provisional and not yet derived from an attack-cost model. A target set too low leaves the security budget inadequate; one set too high imposes an unnecessary cost on holders whenever fees fall short.

**Capital flight.** A store-of-value asset with a carrying cost competes against substitutes without one, including any non-demurrage fork of Bitcoin. This remains the principal risk to the proposal. The target-based design reduces it relative to a fixed rate, because no cost applies while subsidy and fees are sufficient, but does not remove it.

**Perceived confiscation.** Holders observe their effective balances decline whenever the rate is non-zero. This may provoke stronger resistance than dilution, which is not visible on a holder's own balance.

**Implementation determinism.** The demurrage rate, the index and the fee pool must be computed identically across all implementations, using fixed-point integer arithmetic.

**Pre-signed transaction validity.** Implementations must enforce the reference height rules exactly, and Layer 2 software must set `ref_height` on every pre-signed transaction it creates.

**No new incentive to force-close.** Because decay is attributed pro rata in every channel state, a party gains nothing by forcing, delaying or refusing a channel update.

**Privacy.** UTXO age is already public. The `ref_height` field may reveal approximately when a pre-signed transaction was signed; implementations may reduce this by rounding `ref_height` to a coarse interval.

# Reference Implementation

A reference implementation against Bitcoin Core is available at [cpopov/bitcoin#1](https://github.com/cpopov/bitcoin/pull/1). It is not scheduled on any network; on regtest it activates with `-testactivationheight=demurrage@<height>`. It implements:

- the fixed-point demurrage index, per-period rate, UTXO set value, dividend and fee pool, with per-block state stored alongside the block index so that it survives restarts and reorganisations;
- the `ref_height` field, its serialization, validation rules and signature hash commitment;
- the fee pool, its payout rule, and the revised coinbase limit;
- effective-value computation in validation, the mempool, mining, the wallet, PSBT and RPC.

Its `doc/bip462.md` maps each part of this BIP to the code and lists its limitations.

Lightning implementations must set `ref_height` on commitment, HTLC second-stage and penalty transactions, and denominate channel parameters in effective value.

Prior art exists: Freicoin (2012, by Jorge Timón and Mark Friedenbach) implemented demurrage on a Bitcoin-derived codebase, with proceeds recirculated as a perpetual mining reward and a comparable per-transaction reference height.

# Test Vectors

Test vectors are provided in [`bip-0462/test-vectors.json`](bip-0462/test-vectors.json). They were computed with an implementation of this BIP's arithmetic that is independent of the reference implementation's consensus code, and the reference implementation passes all of them. They cover:

1. `rate`: the demurrage rate for a rate period with mainnet parameters, including periods where subsidy and fees exceed the target (rate zero), where they fall short, and rounding edge cases.
2. `index`: demurrage index values over sequences of rate periods.
3. `effective_value`: effective values of outputs created at different indexes.
4. `utxo_value`: normalized values of outputs and the UTXO set value they give.
5. `dividend`: demurrage dividends.
6. `fee_pool`: fee pool balances and payouts across a sequence of blocks.
7. `chain`: a short chain with small parameters, giving for each block its rate, index, dividend, pool payout, coinbase limit, pool and UTXO set value.
8. `inputs`: valid and invalid transactions under each `ref_height` rule, including future reference heights and reference heights earlier than a spent output, with the resulting fees.
9. `transaction`: the serialization, txid and wtxid of a version 4 transaction, and its legacy, BIP 143 and BIP 341 signature hashes.

All fixed-point values are integers scaled by `INDEX_ONE`. Values that do not fit in 64 bits are given as decimal strings. The file is generated by `contrib/bip462/gen_test_vectors.py` in the reference implementation.
